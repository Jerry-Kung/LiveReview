
# LiveReview 前端 UI/UX 重构实施方案

## 1. 重构目标

当前 LiveReview 前端已经具备基础功能，但现有页面偏向传统后台管理系统，存在卡片过多、信息层级弱、视觉风格不统一等问题。

本次任务对前端进行一次完整的 **UI/UX 视觉重构**。

目标是将 LiveReview 打造成：

> **专业、克制、现代、商务化的企业级直播视频分析工作台。**

整体视觉参考本次提供的设计稿：

> **Clean / Minimal / Professional / Enterprise SaaS / Data Workspace**

不要追求“炫酷 AI 风”，不要加入渐变、玻璃拟态、霓虹、3D 等视觉效果。

---

# 2. 本次重构范围

重点重构以下两个页面：

### 页面 A：新建分析任务

用户上传一场直播录屏。

### 页面 B：任务详情

展示：

* 任务信息
* 视频媒体信息
* 当前处理状态
* 视频处理流程
* 视频切片结果

**本次不修改后端业务逻辑，不修改已有 API，不增加新的业务功能。**

如果当前页面已有真实数据，应继续使用真实数据。

# 8. Card 使用原则

这是本次重构的重要要求。

**减少 Card Soup。**

不要：

```text
Card
 └── Card
      └── Card
```

也不要把页面上的每一个信息块都做成独立卡片。

推荐：

```text
Page
 ├── Header
 ├── Processing Section
 ├── Media Information
 └── Video Segments
```

只有真正需要视觉隔离的区域才使用 Card。

Card：

```text
background: white
border: 1px solid #E5E7EB
border-radius: 8~12px
```

不要使用明显阴影。

```text
│ │                                       │ │
│ │       或点击选择本地文件               │ │
│ │                                       │ │
│ │          MP4 / TS · 最大 2 GB         │ │
│ │                                       │ │

│ │                                       │ │

└───────────────────────────────────────────┘
```

右侧增加：

```text
处理说明
```

展示当前系统会执行的处理流程：

```text
01  媒体解析
    检测视频格式、分辨率、编码信息

02  格式处理
    根据视频格式进行必要处理

03  视频切片
    按时间切分视频，生成多个片段

04  完整性校验
    校验切片完整性，确保数据可用
```

这样用户能够理解：

> “上传文件之后，系统到底在做什么。”

# 10. 上传区域

上传区域不要做成传统：

```text
[选择文件]
```

而应作为页面视觉中心。

采用：

* 虚线/浅色边框
* 大面积留白
* 中央上传 Icon
* 主提示文字
* 辅助说明
* Primary Button

Hover：

```text
border → brand blue
background → very light blue
```

Drag Over：

```text
明显但克制的蓝色高亮
```

不要做强烈动画。

这是 LiveReview V0.1 最重要的页面。

顶部采用：

```text
← 返回任务列表

营销直播录屏分析

2026-09-18 02:43
730 MB
1088 × 1920
HEVC / AAC

```

视频缩略图是非常重要的产品元素。

如果当前已有视频文件但没有 thumbnail，可以根据现有能力决定是否使用占位图，不需要为了本次 UI 重构增加复杂的视频处理逻辑。

# 12. Processing Section

这是页面的重要视觉区域。

标题：

```text
处理流程
```

流程：

```text
✓                  ✓                  ✓
媒体解析 ───────── 格式处理 ───────── 视频切片 ───────── 完整性校验
完成                完成                完成                完成
```

如果任务正在处理中：

```text
✓ 媒体解析
    ↓
✓ 格式处理
    ↓
● 视频切片        处理中
    ↓
○ 完整性校验
```

要求：

* 不要设计成传统 CI/CD Pipeline
* 不要使用过于粗大的进度条
* 节点、连线、状态要精致
* 当前步骤需要有明确状态
* 已完成使用绿色小型状态
* 当前步骤使用品牌蓝

---

# 13. Media Information

媒体信息采用两列数据布局。

例如：

```text
媒体信息

时长                    28:03
文件大小                730 MB

分辨率                  1088 × 1920
视频编码                HEVC

音频编码                AAC
采样率                  44.1 kHz

声道                    立体声
流数                    2
```

重点：

**不要使用现在那种大量横向分割线的传统后台表单风格。**

更接近：

> 数据工作台 / Analytics Dashboard

标签使用灰色。

数据使用深色、较粗字体。

---

# 14. 视频切片

视频切片是当前 V0.1 的核心结果。

标题：

```text
视频切片

16 个片段                 总时长 27:30
```

下面使用真正的 Data Table：

```text
┌───────────────────────────────────────────────────────┐
│ 序号 │ 时间范围       │ 时长 │ 文件大小 │ 状态       │
├───────────────────────────────────────────────────────┤
│ 01   │ 00:00–01:43    │ 1:43 │ 37.2 MB  │ ✓ 已上传    │
│ 02   │ 01:43–03:26    │ 1:43 │ 36.8 MB  │ ✓ 已上传    │
│ 03   │ 03:26–05:09    │ 1:43 │ 38.1 MB  │ ✓ 已上传    │
│ 04   │ 05:09–06:52    │ 1:43 │ 37.6 MB  │ ✓ 已上传    │
└───────────────────────────────────────────────────────┘
```

要求：

* 表头浅灰
* 行之间使用非常浅的分割线
* Hover 有轻微背景变化
* 状态使用小型 Icon + 文字
* 不要每一行都套 Card
* 不要使用粗边框

如果切片数量超过可视区域，使用滚动。

# 15. 页面整体信息密度

当前页面存在一个问题：

> 空白区域很多，但是信息组织并不高级。

重构后应该：

**增加有效信息密度，而不是单纯增加内容。**

目标：

```text
Header
↓
任务身份
↓
处理状态
↓
媒体信息 + 切片结果
```

用户进入任务详情后，应该在 **3~5 秒内理解**：

1. 这是哪个任务
2. 文件是什么
3. 处理是否完成
4. 系统做了哪些处理
5. 产生了多少视频切片
6. 当前结果是否正常

Primary：

```text

白色文字
```

Secondary：

```text
白色背景
灰色边框

```

Danger：

仅在真正需要时使用。

按钮不要过大。

例如：


# 19. 状态设计

统一任务状态：

### 已完成

```text
● 已完成
```

### 处理中

```text
● 处理中
```

### 失败

```text
● 处理失败
```

不要设计成非常夸张的彩色 Badge。

状态应该是**辅助信息，而不是页面主视觉**。

# 20. 视觉上需要避免的东西

明确禁止：

```text
❌ 大面积深蓝 Header
❌ 紫色渐变
❌ 蓝紫渐变
❌ 玻璃拟态
❌ 霓虹效果
❌ 3D 图标
❌ 大面积阴影
❌ 过度圆角
❌ Card 套 Card
❌ 每个模块都加边框
❌ 巨大的按钮
❌ 过度动画
❌ AI 科技风装饰
❌ 为了“丰富”增加无业务意义的数据
```

目标不是：

> “看起来很 AI”

而是：

> **“看起来已经是一款成熟的企业软件。”**

# 21. 实施要求

实施前先：

### Step 1

阅读当前前端代码。

确认：

* 技术栈
* 路由结构
* 页面结构
* 当前组件
* API 调用方式
* 当前 UI 组件库

### Step 2

制定前端重构计划。

重点确认：

```text
Layout
Design Tokens
Navigation
Upload Page
Task Detail Page
Shared Components
```

### Step 3

优先完成视觉重构。

**不要修改后端。**

**不要重新设计 API。**

**不要增加业务功能。**

### Step 4

接入当前已有真实数据。

保证：

> UI 重构 ≠ 功能重写。

# 23. 最重要的一条

**不要把本任务理解成“给现有页面换一套 CSS”。**

应该理解成：

> **保留业务能力，对前端的信息架构和视觉表达进行重新设计。**

最终效果应接近本次提供的参考设计图：

> **白色/浅灰工作台 + 左侧任务导航 + 克制蓝色品牌色 + 清晰的数据层级 + 专业表格 + 精致状态反馈。**

同时，**不要为了追求截图中的视觉效果而修改业务逻辑或引入新的业务概念。**
