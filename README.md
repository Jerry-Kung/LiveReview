# LiveReview

LiveReview 是一款面向商业营销直播的录屏理解与复盘工具，将长时视频中的语音、画面与文字整理为可回溯的内容时间线，并生成有依据的总结、评价与改进建议。

> 本文定义项目的目标、顶层方案与 V0 开发规划，供 Coding 工具作为开发依据。所有版本均为计划项；具体代码结构、接口、数据字段与实现细节由开发阶段结合实际验证确定。

## 1. 项目背景与原始需求

商业营销直播通常持续几十分钟至两三个小时，包含产品讲解、优惠说明、产品展示、观众互动和行动引导等内容。人工逐段观看、整理和复盘耗时较长，单纯的语音摘要又容易遗漏画面演示、屏幕文字及音画之间的关联。

项目的原始业务流程如下：

1. 用户通过前端页面上传一场完整直播的录屏文件，典型大小约 1～2GB，当前测试素材为 TS 格式。
2. 后端对视频进行必要的格式处理与分段，使各片段能够输入支持音画理解的模型。
3. 模型识别片段中的语音、画面与文字，产出带时间信息的内容记录。
4. 按原视频时间顺序对齐和整合记录，整理叙事时间线、主题与关键事件。
5. 基于整理后的内容进行复盘，向用户展示分析结论及对应的视频依据。

## 2. 愿景与目标

### 2.1 长期愿景

形成可重复使用的直播复盘能力，将一次性的人工观看转化为可检索、可核查、可比较的内容资产，支持持续优化直播内容、互动方式和营销表达。

后续可按业务需求扩展多场直播对比、行业复盘标准和经营数据关联分析；这些方向不作为 V0 的前置依赖。

### 2.2 V0 目标

- **流程完整**：完成上传、预处理、识别、整理、分析和结果查看的闭环。
- **内容可用**：尽量完整保留语音表达，重点识别产品、价格、优惠条件、展示动作和互动等业务信息。
- **结论可查**：重要事件和分析结论能够关联原始内容，并定位至视频对应时间段。
- **执行可恢复**：处理进度可见，失败时段明确，已完成结果可保留并支持局部重试。
- **效果可验证**：接入真实模型与真实直播素材，通过人工抽查评估识别质量和复盘价值。

“完整识别”作为质量方向，不承诺视频信息无损转写。听不清、看不清、识别失败或证据不足的内容应明确标注，避免通过推测填补。

## 3. 整体设计

### 3.1 方案框架

系统采用分阶段的后台处理流程，各阶段产物可独立查看与复用。

| 阶段       | 主要职责                                           | 主要产出                       |
| ---------- | -------------------------------------------------- | ------------------------------ |
| 视频接入   | 接收文件、建立处理任务、提供进度与历史结果入口     | 原始视频与任务记录             |
| 视频预处理 | 探测媒体信息，按需转换格式、调整体积和切分片段     | 可识别的视频片段及时间对应关系 |
| 多模态识别 | 提取语音、视觉事件和画面文字，标记不确定内容       | 带时间与来源的内容记录         |
| 内容整理   | 对齐时间、处理重叠和跨片段内容，识别主题与关键事件 | 全场内容时间线与章节整理       |
| 复盘分析   | 按业务维度形成总结、问题判断和改进建议             | 附带依据的复盘报告             |
| 结果交互   | 展示内容与报告，支持定位视频、检查缺失和重新处理   | 可核查的复盘工作界面           |

### 3.2 核心设计原则

**保留内容证据，再生成分析结论。**

识别阶段以记录实际内容为主，区分主播原话、画面文字和视觉描述。内容整理负责还原发生过程，复盘分析负责解释和建议，避免早期摘要丢失后续分析所需的细节。

**以原视频时间轴贯穿全流程。**

片段、内容记录、事件和结论均应保留时间关联。重叠片段产生的重复内容需要合并，主播在不同时间真实重复的表达应保留；跨片段话题应能够连续理解。

**分阶段保存，支持局部重新执行。**

长视频作为后台任务处理，不依赖用户持续打开页面。片段识别失败时可局部恢复；调整复盘要求时应能够复用已有识别结果。

**先验证核心链路，再增加能力。**

V0 采用职责明确的固定处理流程，保持模块之间的替换能力。新增模型、工具或基础设施应服务于已验证的具体问题，控制系统复杂度。

## 4. 关键方案策略

### 4.1 视频处理

- 优先支持当前 TS 测试素材，保留原始文件，并按需要生成适合识别和浏览器回看的版本。
- 根据实际编码与媒体状态决定重新封装或转码，确保处理后的内容和音画同步可用。
- 采用几分钟级片段作为初始验证方向，片长与重叠范围结合模型限制、内容密度和实测效果调整。
- 同时考虑输入大小、识别效果与输出长度，避免片段过长导致转写截断或过度概括。
- 保留真实时间对应关系，对关键帧偏移、时间戳异常和片段缺失进行必要检查。

### 4.2 模型识别

V0 优先验证“小片段输入音画理解模型”的统一识别方案。模型选择须确认实际接口能够处理声音、画面与文字，并使用真实直播样本评估，暂不锁定厂商或型号。

重点检查语音遗漏、价格与数字错误、优惠条件遗漏、画面文字可读性和时间定位情况。如统一识别无法达到语音记录要求，再引入独立 ASR；视觉补识别或 OCR 同样按实际缺口引入。

不同识别方式应汇入一致的内容整理流程，避免模型更换影响全部下游能力。

### 4.3 内容整理与复盘

内容整理以真实时间顺序为基础，形成主题章节与关键事件。识别原始记录应持续保留，章节摘要不能成为复盘分析唯一的证据来源。

V0 的初始复盘维度包括：

- 内容结构与讲解节奏。
- 产品卖点表达与展示配合。
- 优惠说明的清晰度及音画一致性。
- 观众问题回应与互动方式。
- 咨询、留资或下订等行动引导。

每条重要判断应说明依据与发生位置，并给出具体改进建议。涉及持续时间、出现次数等可确定计算的指标，优先由程序计算。

仅有录屏时，分析限定于视频可观察的内容与行为；没有曝光、观看、留资和成交数据，不输出未经验证的经营效果或因果结论。观众评论仅以录屏中实际可见且能够识别的内容为依据。

### 4.4 用户交互

前端围绕上传、任务进度、内容时间线和复盘报告组织。用户能够查看已完成和失败的处理部分，并从事件或报告依据跳转至视频对应位置进行核查。

上传与长任务应适配大文件场景，支持必要的失败恢复。局部内容缺失时，应明确显示，不能将不完整结果标记为完整复盘。

## 5. 技术栈

| 层面     | 选型方向                                                     |
| -------- | ------------------------------------------------------------ |
| 前端     | TypeScript，采用 React 或团队熟悉的同类框架                  |
| 后端     | Python，优先采用 FastAPI                                     |
| 媒体处理 | FFmpeg / ffprobe                                             |
| 模型能力 | 音画理解模型与文本分析模型，通过 API 接入；按验证结果补充 ASR 等能力 |
| 后台执行 | 独立后台任务执行单元，负责分阶段处理、有限并发和失败恢复     |
| 业务存储 | 关系型数据库，保存任务、识别内容及分析结果；数据库产品在开发启动时确定 |
| 文件存储 | V0 优先使用持久化文件目录，后续按需要扩展对象存储            |
| 部署     | Docker Compose；环境差异与模型连接配置通过环境变量管理       |

前端框架、数据库产品等未锁定项由开发工具根据项目实际条件选择并记录。该选择不应扩展本阶段业务范围。

## 本地开发

环境要求：Python ≥3.12 + uv、Node ≥20 + npm。Docker Compose 用于测试环境（本地不强制安装 Docker）。

### 后端

```bash
cd backend
uv sync
uv run uvicorn app.main:app --reload   # http://localhost:8000/health
uv run pytest                           # 测试
```

### 前端

```bash
cd frontend
npm install
npm run dev      # http://localhost:5173（已代理 /health 到后端 8000）
npm run test     # 测试
npm run build    # 构建产物到 dist/
```

### 测试环境（Docker Compose）

```bash
docker compose -f docker/docker-compose.yml up --build
```

拉起后前端在 `http://localhost:8080`，后端健康检查在 `http://localhost:8000/health`。

## 6. V0 版本规划

V0 按以下里程碑递增交付，每个版本均须可运行、可测试、可独立验收，并回归已有核心功能。V0.4 完成后形成首个完整 MVP。

### V0.1：长视频处理与切分

**目标**：将完整直播录屏处理为可用的短片段，为后续多模态识别提供输入数据。

**范围**：建立最小可运行环境，支持典型 1～2GB、几十分钟至两三个小时的录屏上传、媒体探测、必要的格式处理与切分，保存原始文件、切片及时间对应关系，提供处理进度与结果查看。本版不依赖模型识别即可独立验收。

**验收要点**：

- 在测试环境使用至少一场符合目标规模的真实 TS 录屏，完成上传、预处理与整场切分。
- 切片能够正常播放、保留声音与画面，并可定位其在原视频中的时间范围。
- 切片覆盖整场视频，片段交界、预期重叠和异常缺失可检查。
- 关闭页面不影响后台处理；处理失败可查看原因并重新执行，已完成切片可供后续版本复用。

### V0.2：基于切片的多模态识别

**目标**：使用 V0.1 产出的短片段验证识别质量，并完成整场直播的分段识别与结果汇集。

**范围**：接入真实模型，先选取已有切片验证音画文字识别，再对整场切片执行后台识别，保存和展示带时间信息的内容记录，支持识别进度查看与失败片段重试。识别输入复用 V0.1 的切分结果。

**验收要点**：

- 使用包含密集讲解、报价、产品展示和互动的真实切片进行人工核查，展示语音、画面与文字记录，并记录主要缺失与错误。
- 明确统一识别方案是否可继续采用，以及是否存在必须补充 ASR 等能力的缺口。
- 至少完成一场真实直播全部切片的识别与结果汇集，各片段记录能映射到原视频时间轴，识别缺口明确可查。
- 单片识别失败可单独重试，已完成的切片与识别结果能够复用，无需重新上传或切分原视频。
- 记录实际处理耗时、模型用量和失败情况，作为后续优化依据。

### V0.3：内容时间线与关键事件

**目标**：让用户能够理解和核查全场直播内容。

**范围**：处理跨片段内容，整理主题章节、关键事件和全场内容时间线，支持视频关联回看。

**验收要点**：

- 时间线按原视频顺序组织，跨片段话题能够连续理解。
- 能定位产品讲解、优惠公布、观众问答和行动引导等实际出现的关键事件。
- 点击事件可回看对应视频，并查看支撑该事件的原始内容记录。
- 人工核查片段交界和关键事件位置，重复、遗漏或时间偏差应记录并处理。

### V0.4：复盘报告与 MVP 闭环

**目标**：形成从完整视频上传到有依据的复盘分析的可用工具。

**范围**：接入复盘分析，提供全场总结、关键问题、有效做法与改进建议，完成报告和视频依据的联动。

**验收要点**：

- 用户可完成上传、等待处理、查看时间线和阅读报告的完整流程。
- 重要结论有实际内容依据与时间位置，建议具体，证据不足时明确说明。
- 改变分析要求后，可以复用已有内容记录重新生成报告。
- 使用真实整场直播进行业务验收，检查报告是否忠实于素材、是否有助于改进直播。
- 在测试环境通过 Docker Compose 运行完整流程，接入真实模型，保留任务和结果。

## 7. V0 边界与开发约束

V0 聚焦用户上传后的离线复盘，暂不包含实时直播监听、平台自动抓取、多场对比、经营数据接入、自动剪辑、自动发布及复杂组织管理。

开发遵循以下约束：

1. **按里程碑推进**：优先完成当前版本目标，每版以实际运行结果验收，不以文档或模块数量替代交付。
2. **以真实素材驱动方案**：模型、片长和辅助识别能力根据实测选择，避免提前固化未经验证的假设。
3. **保持轻量与必要扩展性**：围绕当前流程组织实现，为模型和分析标准的调整保留空间，不提前建设通用平台。
4. **保留核查依据**：原视频、关键中间结果和失败记录应可用于定位问题，质量改进能够回归验证。
5. **详细设计留在实现阶段**：本文不规定目录、类、接口、字段或提示词结构。开发工具应结合实际代码完成设计，并将必要的部署与使用说明补充到 README。
