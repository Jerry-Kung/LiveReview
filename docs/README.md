# 文档体系规范

## 写作与阅读原则

1. **最小范围**：写入、更新、阅读都只覆盖与当前任务直接相关的部分。默认不做全量文档阅读，不读历史归档。
2. **不重复代码**：阅读代码或 docstring 即可掌握的信息不进文档——函数签名、参数表、字段清单、类名方法名清单、路由端点表、UI 布局。文档只写意图、决策、契约、坑与运维知识。
3. **不为小改动写文档**：局部功能调整与 bugfix 不进文档。只有对外契约、设计决策、业务规则、运维流程发生变化时才更新。
4. **一处一事**：同一话题只在归属它的那个目录写一次，其他地方引用而非复述。

## 目录分工

| 目录/文件 | 收录内容 | 何时写 |
|---|---|---|
| `README.md`（本文件） | 文档管理规范本身 | 管理规则变化时 |
| `architecture.md` | 稳定的系统级信息：系统边界、核心模块职责、分层、数据流、外部依赖、关键技术约束 | 系统形态或技术约束变化时 |
| `design/` | 重要功能点与业务流程的长期设计：业务契约、开发约定、各模块设计要点 | 业务规则或跨模块契约变化时 |
| `adr/` | 关键设计决策的背景、备选方案与取舍理由 | 做出不易从代码看出的决策时 |
| `specs/` | 开发任务期间的**临时**产出（需求澄清、plan、实现设计）与历史规划文档 | 开始一项中大型开发任务时；历史版本归档 |
| `runbooks/` | 生产运行知识：部署、配置、故障定位、异常处理、实验操作 | 踩到生产环境的坑或流程变更时 |
| `changelog.md` | 重大功能与里程碑事件，按时间倒序 | 功能上线或实验结论落地时 |

各目录的详细收录标准见其自身 README。

## 文档维护约定

- 所有项目文档统一存放在 `docs/` 目录，不在仓库其它位置散落放置。
- 读写 `docs/` 下任意文档前，先查看本 `README.md` 以确认管理规范与归属目录。
- **版本更新、重大变更时需及时更新文档**——文档与代码同步演进，避免只改代码不更文档。
- history子目录中的文档仅作归档用，不做更新、非必要不阅读。
