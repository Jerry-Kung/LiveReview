# V0.2 设计文档：基于切片的多模态识别

> 本文是 V0.2 的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：`README.md` 第 6 节 V0.2 的验收要点、`docs/README.md` 的文档规范、任务方本次的具体要求。
> 定位：记录本版的方案取舍、契约与验收口径，不规定函数签名与字段清单（那些看代码即可）。

## 1. 目标与验收口径

**目标**：用 V0.1 产出的短片段验证音画理解模型的识别质量，并完成整场直播的分段识别与结果汇集。

本次任务方给出的三条具体要求，也就是本版的实现边界：

| 要求 | 落实方式 |
| --- | --- |
| 视频文件通过 TOS 预签名 URL 接入 | 识别输入不用本地文件上传，而是对片段对象键**现签**一个 HTTPS 地址交给模型 |
| 用「识别出附件视频中的所有人声语音」作为测试题面 | 该题面的措辞作为默认 Prompt 固化在 `llm/prompts.py`，输出格式约束由系统拼接而非让使用者自己写 |
| 单次识别可能耗时几分钟，合理规划超时 | 单次请求超时独立配置（默认 900 秒），并在客户端侧关掉 SDK 内建重试，使重试次数与耗时在任务记录里对得上 |

验收时**识别质量必须人工核查**：抽取包含密集讲解、报价、产品展示与互动的片段，逐条比对语音遗漏、价格与数字准确性。自动化测试只覆盖编排、解析与失败隔离，不覆盖模型答得准不准。

## 2. 接入方案

### 2.1 视频输入

片段在 `tos://dfms/live_review_video_data/clip/` 下，发给模型的是 `ObjectStorage.generate_presigned_url()` 现签的地址。三个取舍：

- **不引入 TOS 内网 client**：预签名地址是模型侧唯一需要的输入，凭据与签名留在存储模块内，模型接入模块只见 URL，更换素材来源不影响模型接入。
- **URL 在发请求之前才生成**：一场直播可能有几十片，队列排到后面时先签的 URL 可能已经过期。每片请求前现签，有效期默认 7200 秒。
- **URL 不进日志**：签名即凭据，日志与失败原因只记录对象键与有效期。

### 2.2 请求形态

与任务方提供的 `python_examples.py` 一致：`responses.create(model, input=[{role: user, content: [input_video(video_url, fps), input_text(prompt)]}])`。`fps` 由 `LLM_FPS` 给出（默认 1）。

### 2.3 输出解析

模型输出格式不稳定，解析器按「尽量读出、如实记账」处理：

- **形态容错**：纯 JSON 数组、```json 围栏包裹、数组前后夹带说明文字、数组被包在 `{"segments": [...]}` 里、只识别到一句话时直接返回单个对象，五类都能读出。
- **取值归一**：键名大小写与常见别名（`start_time` / `start` / `begin_time` 等）、时间字符串（`00:12.5`、`01:02:03`）、毫秒单位（**按片段实际时长判定**，不用固定阈值——`1500` 在一个 300 秒的片段里只能是毫秒，在 3600 秒的片段里就是合法秒数）。
- **丢弃必留痕**：字段缺失、时间倒置、内容为空、非对象的条目都会被丢弃，**每一条都在片段上留下告警文本**。「模型返回了 N 条、入库了 M 条」必须可核查。
- **空数组 vs 解析失败**：`[]` 是有效结果（模型明确说这个片段没有人声）；空输出、没有 JSON 数组、生成被中断都判失败。两者的区别是「静音片段」与「识别失败」，绝不能混。

### 2.4 时间对齐

模型给的是片段内相对秒数，本系统的证据链以原视频时间轴为准，因此落库前统一平移为绝对时间（片段起点 + 相对时间）。原始相对时间一并保留，便于对照模型输出定位偏差。

**越界时段只标记 `out_of_range`，不裁切**：裁切会让下游看到一段「看起来严丝合缝」的时间轴，而实际上模型并没有在那一秒说过那句话。

## 3. 执行与状态

### 3.1 识别是独立阶段

识别不由切分链自动串联，而是由 `POST /api/tasks/{id}/understanding` 手工触发；进程重启也不自动重放。理由是识别要花钱调模型，应当在用户明确意图下发生。

任务行的 `status` / `progress` 仍然只描述切分链，识别写自己的一组 `understanding_*` 字段（含独立的 `understanding_progress`）。这样两组进度不会互相覆盖，也让「切分成功但识别失败」与「识别重跑而切分产物不动」互不干扰。

### 3.2 失败隔离与续跑

- **单片失败不牵连其余片段**：整场状态标为「部分失败」，失败原因落在该片段上（服务端错误带 `request_id`）。
- **配置缺失是整场失败**：缺 `LLM_*` 配置时接口直接返回 503 并列出缺失项名称，不进入执行——否则整场切片会逐片各失败一次。
- **续跑按片判断**：已识别成功的片段跳过，只为未完成与失败的片段发新请求。重复点击不会重复计费。
- **单片重试是同步的**：`POST /api/tasks/{id}/clips/{index}/understanding` 单片通常几十秒到几分钟，同步等待可以让用户立刻看到结果，失败原因直接作为响应返回；整场识别仍走后台。

### 3.3 并发

默认串行（`LLM_CONCURRENCY=1`）。模型侧的限流与配额未知，串行是可预期的起点；提高并发时要注意预签名 URL 的有效期必须覆盖排队时间。并发执行的实现方式是 HTTP 调用放在工作线程、URL 生成与落库留在主线程——数据库会话不是线程安全的。

### 3.4 重试边界

| 情形 | 处理 |
| --- | --- |
| 超时、限流、5xx、生成未完成 | 退避重试，共 `LLM_MAX_ATTEMPTS` 次（默认 3） |
| 4xx 非限流、连接失败、配置错 | 直接失败，不重试——请求本身的问题重试无用 |

每次成功与失败都记录**实际发出的请求次数**（`understanding_attempts`），重试是否被触发过是排查「模型不稳」的关键线索。

## 4. 结果与呈现

### 4.1 三处可核对的结果

| 层次 | 内容 | 位置 |
| --- | --- | --- |
| 整场汇总 | 状态、已识别片段数、语音条数、失败片段数、模型名、起止时间 | 任务接口 `understanding` |
| 逐片明细 | 状态、语音条数、请求次数、完成时间、失败原因、解析告警 | 任务接口 `clips[]` |
| 整场全文 | 按原视频时间轴拼好的语音记录文本 | `GET /api/tasks/{id}/transcript` 与 `/transcript.txt` |

全文由**后端拼装**而不是前端逐片拼接：它是「识别结果汇总」这一对外产物，只在一处生成才能保证页面看到的、复制的、下载的是同一份内容。失败片段在全文里留一行括注而不是被跳过——「整场识别」的完整度必须能被一眼看出。

### 4.2 界面

工作区新增「识别结果」块（排在媒体信息与切分结果之后，对应处理链路的第三个阶段）：

- **汇总**：识别状态、已识别片段数（失败数单独标出）、语音条数、完成时间、模型名。
- **逐片明细表**：序号、时间范围、识别状态（含失败原因与解析告警）、语音条数、请求次数、完成时间，以及**单片重新识别**按钮。
- **全文面板**：默认收起，展开时才拉取（避免轮询期间反复取整场文本）；可复制、可下载 txt；逐条记录也列出，越界条目单独标注。

**识别失败恰恰是最需要重试的情况**，因此失败片段的「重新识别」按钮必须是可用的——这一点在实现中一度写成了「失败即禁用」，属于必须避免的反向设计。

## 5. 数据留档

片段行保留：解析后的条目（含绝对时间与相对时间、越界标记）、**原始返回文本**、token 用量、解析告警、实际请求次数、起止时间。只留解析后的结果会让解析问题无从复现，而验收要看的正是「模型到底回了什么」。

## 6. 范围与后续

本版**不做**：跨片段内容合并（留给 V0.3）、识别结果的人工校正、提示词多轮对比与批量实验、独立 ASR 兜底。

「统一识别方案是否可继续采用、是否存在必须补充 ASR 的缺口」这一条验收结论，要等真实素材跑完人工核查才能给出；本版把判断所需的数据（原始返回、用量、耗时、丢弃条目）都留下来，使该结论有据可依。
