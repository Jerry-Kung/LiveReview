# V0.7.0 设计文档：上传后全自动流程模式

> 本文是 V0.7.0 的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：任务方本次给出的需求（见 §1）与本轮的三条澄清答复。
> 定位：记录本版的方案取舍与边界记账，不规定函数签名与字段清单（那些看代码即可）。

## 1. 本次范围

任务方提出的需求：

> 用户希望在上传完成后自动完成后续的内容理解与复盘分析，不需要再手工点两次按钮。
> 该功能做成「设置」页里的一个可配置开关：打开时开启全自动流程模式，关闭时恢复为各阶段
> 手工点击执行。

本版把「上传 → 处理 → 识别 → 复盘」整条链路收进一个开关。默认关闭，即默认行为与本版
之前完全一致。顺序实现为三步：数据模型与设置接口 → 后端串接 → 前端设置页与文案同步。

### 本轮澄清（需求方答复）

| 问题 | 答复 |
|---|---|
| 开关的生效范围 | **全局一份**，不按账号分 |
| 某阶段失败后是否自动补跑 | **要**，每个阶段最多自动补跑一次 |
| 是否在上传页提供单次覆盖 | **不加**，开关只在设置页 |

## 2. 现状与问题

- 识别与复盘是**两个独立阶段**，各自走 `POST /api/tasks/{id}/understanding` 与
  `POST /api/tasks/{id}/review` 手工触发（见 `docs/architecture.md` 的「后台任务」）。
- 上传完成只把任务推入切分链：`POST /api/uploads/{id}/complete` 收尾时 `submit(task_id)`，
  之后没有任何一处在切分成功后自动接着入队识别。
- 切分链、识别链、复盘链共用 `app/tasks/executor.py` 的一个 `ThreadPoolExecutor`
  （`MAX_WORKERS = 2`），阶段之间靠 `submit(task_id, phase)` 的 `phase` 参数区分。
- 前端「设置」页是 `App.tsx` 里的 `PlaceholderPage`，侧栏那一项带「未接入」标签。
- 没有任何「系统级可变配置」的存放处：`config.py` 全是环境变量，账号虽然在库里
  （V0.5.1 起），但没有承载全局开关的表。

用户侧的摩擦很直接：一场直播处理完之后界面停下来，用户必须自己发现「内容理解」页有按钮，
点一次、等几十分钟、再切到「复盘分析」页点第二次。长任务期间关页面是常态，回到页面时
容易忘记自己停在哪一步。

## 3. 方案取舍

### 3.1 串接放在后端，不做前端连点

前端自动连点（上传完成后依次调两个接口）看着最省事，但不成立：

- **关页面就断**。前端的轮询在用户关闭页面后消失，而「上传后自动跑完」这条承诺必须与
  浏览器无关。这与 `app/uploads.py` 把「收齐后的合并入库」从请求处理里抽出来、
  `executor.requeue_pending` 承接重启恢复是同一个理由。
- **拿不到该动的时刻**。上传完成到入库之间由后端独立完成（合并、对象存储、建任务），
  前端没有一个可靠的事件知道「现在该开始识别了」。
- **业务规则不该放在前端**。「什么时候该串下一阶段」依赖阶段终态、前置产物与模型配置
  三项判断，这三项都是后端的事实。

### 3.2 串接函数是唯一的推进点，调用点有三处

新增 `app/tasks/chain.py`，对外只暴露一个 `advance(task_id, *, from_phase)`：某个阶段
进入终态后调用，由它决定要不要接着跑下一个阶段。三处调用：

| 调用点 | 时机 |
|---|---|
| `runner.py` 的 `run_task` 收尾 | 切分链成功 → 尝试入队识别 |
| `understanding.py` 的 `run_understanding` 收尾 | 识别结束 → 尝试入队复盘 |
| `executor.py` 的 `requeue_pending` | 进程在「上一阶段已结束、下一阶段还没入队」之间被杀时补上 |

第三处是必需的：任务体里 `submit()` 与进程退出之间存在窗口，只补前两处会让这类任务永远
停在「识别成功但没复盘」。补扫的判据是 `auto_run` 且上一阶段已成功而下一阶段还没跑过，
因此它同时覆盖「从未串过」与「串到一半被打断」两种情况。

### 3.3 串接不能从任务体内部 `submit`

`MAX_WORKERS = 2`。如果切分任务体在自己占着线程的情况下调 `submit(..., understand)`，
两个 worker 同时这么做就会双双阻塞在队列上——它们自己就是唯一能消费队列的线程，形成自锁。

因此推进动作收在 `executor.run()` 这个包装里：`run_sync` 跑完（线程已归还）之后才调
`advance`。`advance` 内部失败一律只记日志、不抛——串接失败不能污染已经成功的阶段结论。

### 3.4 开关存库，不用环境变量

一个要在界面上点、且点完要立刻生效的开关，不能是环境变量：那意味着「改完要重启」，以及
「界面设置」与「部署配置」两份要手工同步的清单。V0.5.1 已经为账号做过同一个判断
（`AUTH_USERS` 从环境变量移进 `users` 表），理由相同。

新增单行的 `app_settings` 表（`id = 1`）存 `auto_pipeline_enabled`，而不是做成键值表：
本版只有这一个开关，键值表会引入「键名拼错」「值类型不定」两类不必要的问题。日后开关变多时
再改成键值结构是一次纯机械的改动。

默认值为**关闭**，因此升级到本版不会改变任何已有行为。

### 3.5 任务行留一份开关快照（`auto_run`）

`Task` 新增 `auto_run` 布尔列，在 `create_upload` 建任务时按当时的开关值写死。作用有三个：

- **串接判据不受后续变更影响**。用户中途关掉开关，不该让已经承诺「全自动」的任务半途停在
  识别后；反过来打开开关也不该追溯改变已创建任务的行为。
- **界面能如实标注**。任务详情页据此显示「全自动」，用户不用去设置页猜这条当时是怎么跑的。
- **费用可追溯**。全自动会真的花钱调模型，出问题时需要能查「这批是谁在什么模式下产生的」。

`advance` 要过两道闸：**本任务的 `auto_run` 快照**为真（这条任务创建时承诺了全自动），且
**当前开关**仍为开。快照挡住追溯——创建在手工模式的任务不会因为后来打开开关而被自动拉起；
当前开关挡住「关掉之后继续花钱」——关掉开关的意图是停止自动推进，而推进一个尚未发生的阶段
是廉价的（真正贵的当前阶段照常跑完，见 §3.10）。

### 3.6 自动补跑一次，用计数列封顶

识别失败往往来自一次瞬时抖动（`llm_max_attempts` 用尽、预签名地址生成失败）。只串接不补跑
的话，一次抖动就把「全自动」停在失败上，用户仍要回来点按钮——那这个功能就没兑现。

`Task` 新增 `auto_retries` 整数列，每自动补跑一次加一，达到上限（`AUTO_RETRY_LIMIT = 1`）
后不再补。补跑走与串接同一套 `submit`，不绕回 HTTP 入队接口：

- 绕回接口会把逻辑兜进 HTTP 层，还要处理「接口自己拒绝」（如 409「识别正在进行中」）这类
  与本场景无关的分支。
- `run_understanding` 会跳过已成功的片段，只补失败的，因此补跑不会重复计费。
- 复盘补跑最多重跑一次文本调用。

**该计数描述「当前在途阶段」的补跑次数，串入新阶段时归零。** 一个整数列要同时服务于识别与
复盘两个阶段，只有归零才能表达「正在跑的这个阶段补过几次」；归零发生在串接成功入队的那一刻，
因此它读出来永远对应当前阶段。计数列比布尔量更能容日后调整策略（例如改成 2 次），且旧库
补列时带库侧默认值即可。

### 3.7 「部分失败」照常往下串

识别整场状态为 `failed` 时可能有两种含义，分开处理：

- **有片段成功、个别片段失败**（`understanding_clip_count > 0`）：**先按 §3.6 自动补跑一次**
  （只重发失败的那些片段），补跑结束后无论结果如何都**串到复盘**。这与现有手工流程一致——
  复盘输入是已落库的转写，`merge_reviews` 会把缺口写进分析等级与「本场不足以判断」。让
  用户拿不到任何结论，比给一份标注了边界的结论更糟。
- **一片都没成功**（`understanding_clip_count == 0`）：停，不串。此时复盘的任务体自己会
  以 `REVIEW_SKIPPED` 短路（`run_review` 没有可用记录时直接跳过），串过去只是白跑一趟流程
  并在界面上留下一条「无输入」的记录。

### 3.8 模型未配置时不串，落成可解释的失败

`advance` 在进入模型阶段前先看 `settings.llm_configured`。未配置时直接落成该阶段的失败态
并写明「模型未配置，补齐 `LLM_*` 后重新执行」，而不是入队一个注定逐片失败的阶段。

这与 `llm_configured` 的既有语义一致：模型配置缺失不算服务降级，切分链路不依赖模型。

### 3.9 开关只管「此后新上传」，不追溯

打开开关不会自动拉起历史上「已处理完但从未识别」的任务。理由：

- 那些任务的视频可能已过 72 小时保留期，串过去必然失败。
- 「一次点击让系统把所有历史任务都跑一遍模型」是用户没有表达的意图，且是真实花费。
- 这与 `reclaim_interrupted_understanding` 现有的「只翻曾经启动过的任务」是同一条原则。

### 3.10 关掉开关不打断已在跑的阶段

开关在「下一次 `advance`」处读取，因此关掉后：正在跑的识别跑完就停，不再串复盘，任务行上的
`auto_run` 快照保持为真（它记录的是「这条任务创建时是什么模式」）。不做「中断当前阶段」的
语义——给一个已经花了钱的模型调用加取消路径，收益远小于复杂度。

## 4. 未做（边界记账）

- **不做按账号的开关**：本版没有用户隔离，所有账号看到同一套任务数据。按账号存会让同一个
  列表里不同任务行为不同，却找不到界面上的解释。
- **不做上传页的单次覆盖**：需求方明确不加。想单独手工控制某一场，需先去设置页关掉。
- **不做自动重试切分链**：切分失败（探测 / 转封装 / 切分 / 覆盖校验）不自动重跑。它是本地
  算力，重跑一次是几十分钟的机器时间，且失败原因通常是素材本身的问题，重跑不会变好。
- **不做多阶段流水线的并发编排**：`advance` 只推进「本任务的下一个阶段」，不做跨任务的
  排队与优先级。
- **不做过期任务的自动重传**：视频过期后仍需用户重新上传（V0.6.1 的语义不变）。
- **不做串接失败的重试队列**：`advance` 抛错只记日志。真正的兜底是启动补扫
  （§3.2 的第三处调用），因此「进程存活期间 submit 失败」会留到下次重启时补上。
- **不引入设置项的审计历史**：只记 `updated_at` 与 `updated_by`，不做变更流水。
- **`specs/` 下的本文不做长期维护**：长期契约写进 `docs/architecture.md`。

## 5. 验收标准

1. 开关默认关闭；关闭时全链路行为与本版之前**完全一致**（不自动串接、不自动补跑）。
2. 打开开关后，上传并处理成功的任务自动接着识别，识别结束后自动接着复盘，全程无需点击、
   关页面不影响。
3. 两道闸都生效：创建在手工模式的任务，事后打开开关也不会被自动拉起（不追溯）；创建在
   全自动模式的任务，事后关掉开关则不再串入后续阶段。任务行上的 `auto_run` 快照与创建时
   的取值一致，且界面可见。
4. 识别有片段失败时自动补跑**一次**（只重发失败的片段）；补跑结束后只要有片段成功就继续
   复盘，一片都未成功则停在该状态不再补跑。`auto_retries` 记录当前在途阶段的补跑次数，
   串入新阶段时归零。
5. 识别一片未成功时不串复盘；模型未配置时不入队，落成带可操作文案的失败态。
6. 进程在「阶段已结束、下一阶段未入队」之间被杀时，重启后补扫能接着串下去。
7. 设置接口：读对所有登录账号开放，写只对管理员（非管理员 403），写入立即对**新上传**生效。
8. 设置页能读到并切换开关；非管理员看到开关的当前状态与说明，但没有可点的入口。
9. 新建任务页的使用说明随开关切换文案：关闭时说「识别与复盘需要点按钮才会开始」，打开时
   说「上传后会一路自动跑完」。
10. 任务详情页对 `auto_run` 为真的任务显示「全自动」标记。
11. 升级到本版不改变已有数据：`app_settings` 表由 `create_all` 新建，`tasks` 两个新列由
    启动补列加上，旧任务 `auto_run` 为假。

## 6. 测试环境待验（本机未覆盖）

- **真实模型下的全自动端到端**：本机只有假模型客户端，模型费用、长耗时、并发下的表现需在
  测试环境用真实素材验证；重点是「识别失败后补跑一次」这条路径的真实触发。
- **关页面后的继续推进**：确认浏览器关闭期间识别与复盘照常推进，重新打开页面时看到的是
  推进后的状态（本版没有前端改动，但这是该功能的核心承诺）。
- **补扫路径**：在「切分成功、识别尚未入队」的窗口内重启后端，确认 `requeue_pending` 把
  识别补上（本机用例覆盖的是逻辑，时间窗口需在容器里用日志确认）。
- **费用观察**：打开开关后连续上传数条素材，核对模型侧的调用量与任务行的 `auto_run` /
  `auto_retries` 一一对应。
