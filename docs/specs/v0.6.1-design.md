# V0.6.1 设计文档：项目数据自动清理机制

> 本文是 V0.6.1 的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：任务方本次给出的三条初始设计要求（见 §1）与本轮的澄清答复。
> 定位：记录本版的方案取舍与边界记账，不规定函数签名与字段清单（那些看代码即可）。

## 1. 本次范围

任务方给出的三条要求：

1. 本地不存任何视频文件（上传原件、格式转换产物、切分后的片段都不留），推送到对象存储后清理本地磁盘上的视频数据。
2. 对象存储中的视频文件设 72 小时过期机制，到期自动删除。
3. 某任务的视频在 72 小时到期时仍未完成内容理解，则要求用户重新上传。

V0.6 的总目标是「为初版 Demo 正式上线做必要优化」，本版解决其中的存储成本问题：试用期内
长时录屏（单文件 1～2GB、切片动辄几十片）会迅速挤满测试环境本地磁盘与云端桶。

顺序实现为三步：本地视频文件清理 → 72 小时过期与定时清理 → 前端过期引导与文档。

### 本轮澄清（需求方答复）

| 问题 | 答复 |
|---|---|
| 测试环境是否已有可用的 bucket 与凭证 | 已有，凭证在手 |
| 过期后重新上传的期望行为 | **重跑整任务**，不做断点续跑 |
| 72 小时删除的实现方式 | **应用层定时清理**（不依赖存储侧生命周期规则） |

## 2. 现状与问题

- 本地产物集中在 `MEDIA_ROOT`（`app/media/paths.py` 统一约定）：`chunks/`、`assembling/`、
  `originals/`、`converted/`、`clips/`。
- **本地会长期保留视频**：`app/uploads.py:finalize` 把合并产物转存为 `originals/{任务 id}{后缀}`
  供探测与切分使用；`app/tasks/runner.py` 的 `_process` 只在**切分成功后**才删原始副本与
  转封装产物，**失败时二者都保留**（原意是便于在容器内复现）。
- 对象存储已接入（`app/storage/`，TOS 实现 + 内存 Mock），但视频**永久留存**，没有任何回收。
- 项目**没有任何定时调度机制**：唯一的周期性工作是启动时一次性的 `requeue_pending`。

## 3. 方案取舍

### 3.1 「本地不存视频」的落点收在一处

释放动作放在任务体最外层的 `finally` 里（`_process` 包住 `_run_pipeline`），成功与失败
都执行。不逐个环节去改的理由是：只要有一处漏掉，那个文件就会永久占盘，而漏掉是迟早的事。

**这是本版明确的行为变更**：失败任务不再保留本地副本，复现失败需从对象存储重新取回。
代价是可接受的——`_prepare_local_source` 本就实现了「副本缺失则按对象键回下载」，重试路径
不需要新增逻辑；而把 GB 级文件长期留在盘上，在测试环境会直接把磁盘挤满。

上传入库成功后也立即释放副本（`finalize` 的 `_drop_local_copy`）。注意顺序：体积必须在
删副本之前取好，否则 `task.size` 会退化成声明的字节数。

### 3.2 过期是「只删视频、不删结论」

到期后删除对象存储中的原始视频与全部切片，清空 `tasks.object_key`，**但保留转写与复盘
结论**——它们早已落库，与视频是否还在无关。因此已出结论的历史任务仍然可以查看与下载
报告，只是不能再启动或重试识别。

由此出发，识别/重试识别的入口按「视频是否还在」（`object_key` 是否为空）拒绝，返回 409
并说明要重新上传。

### 3.3 复盘不因过期被拦（对本轮规划的偏离）

规划阶段曾打算给 `start_review` 也加上过期闸门，实现时放弃：复盘读的是**已落库的识别
结果**，不碰视频，因此过期并不妨碍复盘。加上闸门会与 §3.2 的目标直接冲突——用户手上
明明有一份可用的转写，却被禁止产出结论。口径统一在这里让位于「结论要留得下来」。

### 3.4 重传＝新建任务，不新增接口

过期任务的「重新上传」由前端先调用既有的 `DELETE /api/tasks/{id}` 清掉旧记录，再回到
上传入口。不在原任务上续跑是因为视频、切片、识别结果全部作废，复用旧任务只会留下一个
半新半旧的记录（旧切片行、旧识别结果）。清掉后新建任务，语义与「从头重跑」一致。

### 3.5 定时清理是进程内守护线程

与既有的进程内线程池同一条实现路线（单实例部署，横向扩展不在范围内）。每轮单独捕获
异常：网络抖一下不该让清理永久停摆。`CLEANUP_ENABLED=false` 可关掉，供测试与本地开发
使用。

在途任务一律跳过（`processing` / 识别中 / 复盘中）：任务体正在读那个对象，删除只会制造
半个世界的状态。跳过不是放弃——下一轮扫描时它大概率已经跑完。

删除失败时**保留 `object_key` 与未标记状态**，下一轮重试；否则会留下永远无人回收的孤儿
对象，而数据库里已经没有任何线索能定位它。

### 3.6 过期状态独立成字段，不复用 `status`

`status` 只描述切分链（`uploading` / `uploaded` / `processing` / `succeeded` / `failed`），
这是 V0.1.5 起就确立的约定，本版沿用。过期的任务其 `status` 很可能仍是 `succeeded`，把
它塞进 `status` 会覆盖掉「切分成功过」这个事实。

### 3.7 启动时清扫无主残留

`finalize` 与任务体之间有一个窗口：副本已落盘、任务还没被认领，此时进程被杀就会留下
无人认领的文件。启动时（与 `requeue_pending` 同处）按「库里是否还有对应任务/会话」清一遍，
只清无主的，避免把正在上传的分片误删。

## 4. 未做（边界记账）

- **不做用户隔离**：任务数据不按账号切分（V0.5 起的既有边界，本版未触及）。
- **不做过期前的续期或提醒**：到点即删，没有「即将过期」的通知，也没有手动延期的入口。
- **不做手动触发清理的接口**：清理只有定时线程与启动清扫两条路径。
- **不依赖存储侧生命周期规则**：需求方选定应用层实现，因此桶上不需要额外配置。
- **不做断点续跑**：过期后重传是整任务重跑，已确认的语气。
- **多实例部署会重复扫描**：删除是幂等的，重复执行的危害有限；横向扩展仍不在范围内。
- **失败任务的本地副本不再保留**：复现需从对象存储取回（§3.1）。
- **`reset_task_for_retry` 不清 `video_expired_at`**：过期任务的 `object_key` 已被清空，而重试接口在 `object_key` 为空时直接拒绝，因此这条重置路径对过期任务不可达；不为一条走不到的路径加字段清理。若日后放宽重试的准入条件，需一并处理这里。

## 5. 验收标准

1. 处理成功与失败的本地磁盘上都**不残留视频文件**（`originals/`、`converted/`、`clips/` 为空），上传入库后副本即释放，`task.size` 仍正确。
2. 副本缺失时任务体从对象存储取回并跑完，重试路径不受影响。
3. 到期任务的对象（原始视频与切片）被删除，`video_expired_at` 落库，转写与复盘结论不变。
4. 未到期、在途、删除失败三类情况均不被误处理（分别：不动、跳过、保留待重试）。
5. 过期后识别与重试接口返回 409 且文案可操作；转写接口照常可读。
6. 启动清扫只删无主文件。
7. `CLEANUP_ENABLED=false` 时不启动清理线程；单轮失败不终止线程。

## 6. 测试环境待验（本机未覆盖）

- **真实 TOS 上的删除与过期**：本机只有内存 Mock，删除语义（幂等、无权限/网络失败的处理）
  需在测试环境用真实凭据验证。
- **宿主磁盘不再累积视频**：部署后观察 `backend/media/` 在一轮上传+处理后是否只剩空目录。
- **端到端时效验证**：把 `STORAGE_VIDEO_TTL_SECONDS` 临时调到几分钟、`CLEANUP_INTERVAL_SECONDS`
  调到几十秒，传一条 1～2GB 素材，确认桶内对象被清、界面出现「视频已过期」与重新上传入口。
- **反向代理下的 409 文案**：确认过期任务的报错能原样透传到浏览器（V0.5.1 曾在此处踩过
  `Origin`/`Host` 的坑）。
