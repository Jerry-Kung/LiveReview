# V0.1.5 设计文档：预处理与切分

> 本文是 V0.1.5（预处理与切分）的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：`README.md`、`docs/specs/v0.1-plan.md` 第 4 节 V0.1.5、`docs/specs/v0.1.4-design.md`、`docs/README.md` 文档规范。
> 定位：记录 V0.1.5 的选型决策、处理链路与模块边界，不规定函数签名逐个参数、字段清单等实现细节。

## 1. 目标

把整场直播录屏处理为可用短片段：统一转为 MP4、按「时长 + 体积」双约束切分、生成片段与原始时间轴的对应关系、片段落对象存储，并在完成前做整场覆盖校验。这是 V0.1 的核心交付。

## 2. 需求澄清（来自本次开发的任务方要求）

| 要求 | 落地方式 |
| --- | --- |
| 切分前统一转换为 MP4 | 非 MP4 容器（TS 录屏）先转封装为 MP4，之后所有切分都基于该 MP4 |
| 全程不丢音频 | 转换与切分统一带 `-map 0`（保留全部音视频流），且都不重编码；每片上传前校验音视频流齐全 |
| 每片 ≤1GB 且 ≤60min | `SPLIT_MAX_CLIP_BYTES`（默认 1GiB）与 `SPLIT_MAX_DURATION_SECONDS`（默认 3600）从环境变量读取 |
| 不打乱片段顺序 | 片段序号 `index` 从 0 递增，按时间轴顺序切、顺序上传、按序号展示与复用 |
| 只向 TOS 传切分后的 MP4 片段 | 转封装产物与原始文件都不上传；只上传 `clip/` 前缀下的片段，上传成功即删除该片本地文件 |

## 3. 选型与决策

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 触发方式 | 探测成功后**自动串接**切分，沿用 `Task(kind="ingest")`，不新增任务类型与触发按钮 | 一次上传对应一次处理，用户不必理解「先探测再切分」；沿用既有状态机、进度、失败重试与删除语义，改动面最小 |
| 转换策略 | TS → MP4 用 `ffmpeg -c copy`（转封装），不重编码 | 录屏码率已满足需求，转封装在 GB 级文件上只需几分钟且不改动音视频数据；重编码会二次劣化画面并显著拉长耗时 |
| 切分策略 | `-c copy` 按时间点切，不做重编码 | 片段与原素材逐帧一致；代价是切点落在关键帧上，首片起点与原计划可能有百毫秒级偏移，由覆盖校验与容差覆盖 |
| 已是 MP4 时 | 跳过转换，直接用于切分 | 满足「不过度处理」，避免一次无谓的 GB 级复制 |
| 容器识别 | 用探测得到的 `format_name` 判断（`mov,mp4,m4a,3gp,3g2,mj2` 视为 MP4） | 以容器真实内容为准，不比扩展名可靠 |
| 转换产物落点 | `{media_root}/converted/{任务 id}.mp4` | 与 `originals/`、`chunks/` 同级，按任务 id 命名便于定位与清理；由 `paths.py` 统一约定 |
| 转换后校验 | 对产物重新探测，比对时长、时长比例、流数、音频流数 | 转封装在时间戳异常的源上可能产出音画错位或丢流的 MP4；校验不过即判定失败并给出原因，不做静默降级 |
| 转换失败回退 | 本版不自动重编码 | 自动回退会让失败变得不可解释（用户看到的是「转封装失败」却已被悄悄重编码，耗时与画质都变了）。失败原因落库并提示可用 `FFMPEG_*` 参数与源文件排查 |
| 切分计划 | 先按最大时长均分，再对超体积的片段递归对半，直到满足体积上限 | 递归对半保证片段长度尽量均匀且**顺序不变**（子片段原地展开），避免出现一个特别短的尾巴 |
| 片段命名与对象键 | 文件名 `clip_{index:03d}.mp4` 供展示，对象键由 `build_object_key(..., kind="clip", ...)` 生成 | 序号保证顺序可读，对象键保证桶内不重名；键在首次生成后入库，重试复用同一个键 |
| 断点续跑 | 片段已上传（`uploaded` 状态）则重试时跳过，其余重新切分与上传 | `-c copy` 切分是纯函数式的，重跑结果一致，因此已完成片段可安全复用，重试不必从头上传 |
| 进度语义 | 0 认领 → 20 探测 → 25 转换 → 40~98 按片段推进 → 100 完成 | 转换与切片耗时占大头，进度落在真实推进的片段数上，不造拍脑袋的百分比 |
| 覆盖校验 | 完成后比对首片起点、相邻片首尾相接、末片覆盖到总时长（容差 1 秒），问题列表入库 | 验收要求「交界、重叠、缺失可检查」；问题以列表而非布尔入库，便于定位到具体片段 |
| 原视频去留 | 探测成功后**不再删除**本地副本，留给切分使用；切分成功（含上传）后删除 | 删除会让切分必须先花几十分钟从 TOS 取回 2GB 文件；保留副本使「上传 → 探测 → 切分」在同一容器内一次跑完 |
| 接口契约 | `TaskResponse` 增加 `clips`（序号、起止秒、时长、字节数、状态、错误、预签名地址）与覆盖校验结论 | 前端在 V0.1.6 才做结果页，本版先让片段可见、可核对、可下载 |

## 4. 模块边界

```
backend/app/
├─ media/
│  ├─ paths.py            # 新增 converted/ 与 clips/ 的路径约定（与 originals/ 同处一处）
│  ├─ ffmpeg.py           # 新增：ffmpeg 子进程调用（参数构造、超时、输出上限、错误映射）
│  ├─ convert.py          # 新增：容器判定、转封装、产物校验
│  ├─ split.py            # 新增：切分计划（双约束）、单片切分、单片校验
│  ├─ coverage.py         # 新增：整场覆盖校验（交界、重叠、缺失、首尾）
│  ├─ cli.py              # 扩展：支持对某个任务的转换产物与片段做核对
│  └─ probe.py            # 不变
├─ models.py              # 新增 MediaClip 表；Task 增加转换产物与覆盖校验字段
├─ schemas.py             # TaskClipResponse、TaskResponse.clips / coverage_issues
├─ tasks/runner.py        # 任务体扩展为「探测 → 转换 → 切片 → 上传 → 清理」
├─ deletion.py            # 删除任务时一并清理片段对象、片段文件与转换产物
├─ routers/tasks.py       # 只透出片段与覆盖结论，本版不新增路由
└─ config.py              # 切分与 ffmpeg 配置项
```

依赖方向不变：`tasks` → `media` / `storage` / `models`；`media` 只依赖配置与标准库，不感知数据库、HTTP 与对象存储。

### 4.1 处理链路

```
原始本地副本 (originals/{id}.ts)
  │ 探测（V0.1.4）
  ├─→ 已 MP4？ ──是──→ 直接作为切分源
  │                └─否─→ 转封装 → converted/{id}.mp4（+ 产物校验）
  │
  ├─→ 切分计划（时长上限 + 体积上限）
  ├─→ 逐片切分 → clips/{id}/clip_000.mp4 …（+ 单片校验：有音频、有视频、体积达标）
  ├─→ 逐片上传 → clip/ 前缀对象（上传成功即删本地片段文件）
  ├─→ 覆盖校验（交界、重叠、缺失、首尾）
  └─→ 清理：转换产物、原始副本
```

任一步失败：任务 `failed`，原因写入 `Task.error`；已完成上传的片段保留，`retry` 时按序号复用。

### 4.2 状态机延伸

状态机不变（`uploading` → `uploaded` → `processing` → `succeeded` / `failed`），本版只填充 `processing` 内的任务体：

1. 认领任务，`progress=0`。
2. 准备本地副本：`originals/` 下存在则直接用；不存在且已记录的容器不是 MP4 时按对象键取回（`progress=20`）。
3. 探测（已有结论时复用任务行上的字段，避免重复读整文件）。
4. 判定容器并转封装（`progress=25`），产物校验不过即失败。
5. 计算切分计划，与既有片段行按序号 + 起止时间比对，一致且已上传的片段跳过。
6. 逐片切分 → 校验 → 上传，每片完成推进进度（40 ~ 98）。
7. 覆盖校验，结论入库。
8. 清理转换产物与原始副本，`progress=100`，状态转 `succeeded`。

`reset_task_for_retry` 清空探测字段与覆盖结论，**保留片段行**：片段行是「已上传产物」的唯一线索，删掉会让重试重复上传全部片段。

## 5. 配置

`.env` 新增（`.env.example` 同步）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SPLIT_MAX_DURATION_SECONDS` | `3600` | 单个片段的最长时长（秒），≤60min |
| `SPLIT_MAX_CLIP_BYTES` | `1073741824` | 单个片段的最大字节数（1GiB） |
| `SPLIT_MIN_CLIP_SECONDS` | `1.0` | 递归对半的下限；到达下限仍超体积则判定失败并给出原因 |
| `SPLIT_TIMEOUT_SECONDS` | `600` | 单次转封装/切片调用的超时（秒） |
| `FFMPEG_MAX_OUTPUT_BYTES` | `8388608` | ffmpeg stderr 的收集上限 |

`FFMPEG_PATH` 与 `FFPROBE_PATH` 一致，放宽为 `str | list[str]`，本地测试用假 ffmpeg 脚本替换真实工具。`FFMPEG_PATH` 本版起实际使用。

## 6. 前端

- 任务成功后展示：片段数、总时长、覆盖校验结论（通过 / 问题列表）。
- 片段列表：序号、时间区间（`mm:ss ~ mm:ss`）、时长、体积、状态；上传完成的片段给出可点击的预签名下载地址。
- 切分失败沿用既有 `error` 通路与「重新执行任务」入口，不新增页面。
- 结果页、时间线与回看定位属 V0.1.6。

## 7. 错误处理与安全

- 失败原因分类落库：ffmpeg 缺失/不可执行、超时、ffmpeg 报错（含 stderr 摘要）、产物校验不过（时长偏差/丢流/缺音频）、超体积无法再分、上传失败（含存储 `request_id`）。
- 单次 ffmpeg 调用失败不吞掉已完成的片段：已完成片段状态保留，失败原因指向当前片段序号。
- 片段与转换产物不入仓库与镜像（`MEDIA_ROOT` 已由 `.gitignore` / `.dockerignore` 排除）。
- 预签名地址只在接口响应中生成，不入库、不打日志。

## 8. 测试

**本地（Mock 存储 + 假 ffprobe + 假 ffmpeg）**：

- 切分计划：按时长均分、按体积递归对半、顺序保持、恰好整除不产生空尾片、到达下限仍超体积时失败、非法参数报错。
- 覆盖校验：首片不从 0 起、中间缺口、相邻重叠、末片未覆盖到底、容差内视为通过。
- 容器判定与转封装：已是 MP4 直接复用不再调 ffmpeg、非 MP4 转封装并校验、产物时长偏差/丢音频判定失败、ffmpeg 非零退出与超时映射、可执行文件缺失的明确提示。
- 切分调用：参数带 `-map 0` / `-c copy` / `-avoid_negative_ts`、单片校验判定、输出文件缺失报错。
- 任务链路：三约束下走完整链路（片段顺序、对象键前缀、片段行入库、覆盖结论、清理本地产物）、探测成功不再删除原副本、已上传片段在重试时跳过、未完成片段重试后补齐、转换产物存在时跳过重复转换、删片段文件失败不影响任务结论。
- 删除链路：删除任务时片段对象、片段文件与转换产物一并清理。
- 既有 V0.1.1～V0.1.4 测试全部回归通过。

**前端**：片段列表渲染、覆盖校验结论渲染、切分失败展示原因与重试入口、无片段时不展示空列表。

**测试环境（仍需验证）**：真实 TS 录屏的转封装耗时与产物音画同步、片段体积与时长是否落在阈值内、整场覆盖校验通过、`python -m app.media.cli` 对转换产物与片段的核对输出。

## 9. 验收要点（对应 `v0.1-plan.md` 第 4 节 V0.1.5）

- 使用至少一场符合目标规模的真实 TS 录屏完成整场切分。
- 切片可正常播放、保留声音与画面，可定位其在原视频中的时间范围。
- 切片覆盖整场视频；片段交界、预期重叠与异常缺失可检查。
- 已完成切片可供后续版本复用，无需重新上传原视频。

## 10. 不在本版范围

- 结果页、时间线与切片回看界面（V0.1.6）。
- 自动重编码回退与码率自适应：仅按需转封装，不引入转码策略与硬件加速。
- 片段内的二次细分（如按内容密度动态调整片长）与重叠窗口设计：本版片段不重叠，重叠策略留待接入识别后按模型输入限制评估。
- 多任务并行切分的限流与优先级（沿用既有线程池配置）。
- 切分产物的版本留存与人工编辑。

## 11. 已知限制

- 本机（Windows）未安装 FFmpeg，子进程调用层的真实行为只在测试环境验证；本地以假脚本覆盖调用、错误映射与编排逻辑。
- `-c copy` 的切点落在关键帧上，片段实际起止与计划值可能有百毫秒级偏差（覆盖校验容差 1 秒）；若要精确到帧需重编码，本版不引入。
- 切分期间会同时存在原始副本、转换产物与片段文件，峰值磁盘约为原视频的 2～3 倍，测试环境需保证 `liverreview-media` 卷容量（按 2GB 素材预留 6GB 以上）。
- 表结构新增 `MediaClip` 表与 `Task` 字段后，测试环境必须重建 SQLite 文件（`create_all` 不改已存在的表），见 `docs/runbooks/deployment.md`。
