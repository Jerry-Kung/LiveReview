# V0.3 设计文档：直播内容复盘（合并原 V0.3 + V0.4）

> 本文是 V0.3 的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：任务方本次的规划要求、任务方提供的《直播复盘分析准则》（`docs/直播复盘分析准则.md`）、
> `README.md` 第 6 节的 V0.3 / V0.4 预置规划（本版按任务方要求合并）。
> 定位：记录本版的方案取舍、裁剪口径与验收标准，不规定函数签名与字段清单（那些看代码即可）。

## 1. 为什么合并 V0.3 与 V0.4

原预置规划把「内容时间线与关键事件」与「复盘报告与 MVP 闭环」分成两版。两版的核心依赖是同一个：
一份可被分析的整场内容。V0.2 已经产出带原视频时间轴的整场语音转写，也就是这个依赖已经具备。

同时，原 V0.3 的验收要点里有两条**以视频切片播放为前提**（点击事件回看对应视频、片段交界人工核查），
而切片播放功能已撤销。因此本版把两版合并，目标收缩为一条：

**接入直播内容复盘，完成业务闭环** —— 上传 → 切分 → 识别 → 复盘 → 结论展示。

## 2. 输入边界：只有语音

《直播复盘分析准则》面向「视频 + 音频 + 巨懂车数据 + 主播档案」的完整形态。本系统当前只有**整场语音转写**
一类输入，因此准则的使用方式是**裁剪**而不是改写：保留与语音内容有关的分析套路，删掉不可观测的部分。

| 准则中的内容 | 本版处理 | 理由 |
| --- | --- | --- |
| 品牌与业务背景、直播原则、评判口径 | 保留 | 判断表达方式需要业务标准，与输入形态无关 |
| 核心业务链路与漏斗概念 | 保留为背景，**不做瓶颈定位** | 曝光/进入/停留/互动/留资均不可观测，定位必然是凭空推测 |
| 内容主题分类 A~H | 保留 | 只依赖讲的是什么 |
| 讲车表达方式分类（参数直给/场景翻译/…） | 保留，但**不得断言「更有效」** | 有效性需要数据验证，当前没有 |
| 六维能力 | 保留为分析维度，**不做 100 分制打分** | 没有分钟级数据，打分是伪精确 |
| Step 5/6/7 巨懂车数据与时间轴交叉验证 | 删除 | 无数据 |
| Step 1 主播档案、上次问题追踪、Step 12 档案更新 | 删除 | 无历史档案，且跨场比较需要至少 2 场数据 |
| Step 8 评分、Step 13 最佳实践沉淀 | 删除 | 沉淀的前提是「至少 2 场验证」，本版无此能力 |
| 关键帧、OCR、主播行为识别 | 删除 | 本版不做视觉识别 |
| 证据分级、强制分析规则、TOP3 约束、报告结构 | 保留 | 这些是质量约束，与本版最需要的正是它们 |

准则里的「ASR 质量评级 A/B/C/D」被改造为**分析等级**，因为约束对象变了：原文档评的是转写能否
逐句引用，本版要说明的是**这份复盘结论建立在多少素材上**。

## 3. 提示词设计

### 3.1 复盘的固定系统提示词

裁剪后的准则 + 输出契约固化在 `backend/app/llm/review_prompts.py` 的 `REVIEW_SYSTEM_PROMPT`
与 `REVIEW_OUTPUT_INSTRUCTION` 中，作为 system 消息发出；用户消息只承载本场的转写内容与覆盖面。
两者分开是为了让「准则」与「素材」在模型侧有明确的角色区分。

三处与准则原文的**主动偏离**，都是为了让结论在缺数据的条件下仍然站得住：

- **漏斗仅作背景**：准则要求「先定位漏斗瓶颈再归因给主播」。没有数据时这一步做不了，因此提示词
  明确写了「不做瓶颈定位」，并把归因范围限定在内容表达 / 话术方法 / 节奏流程 / 互动响应四类——
  流量、产品、政策、设备这些原因在本版无法判断。
- **不做评分，改定级**：分析等级分「完整 / 部分 / 受限」三档，由覆盖面与转写质量决定。
  等级写入结论并由**程序兜底校正**（见 3.3），不经模型单方面判定。
- **禁止历史比较**：准则要求「复盘开头检查上次问题有没有改善」。没有历史数据时这只能靠编造，
  因此提示词要求只做本场内部比较（如前后半场）。

### 3.2 识别提示词的语气捕捉

准则里「语气与情绪」「镜头表现」「讲车表达方式」等维度需要语气信息，而 V0.2 的转写只有内容与时间。

因此在识别题面（`backend/app/llm/prompts.py`）上做了最小扩展：要求模型判断每句话的语气与情绪，
输出契约增加 `tone` 字段。三个设计点：

- **语气是主观估计**：契约里写明「听不出明显语气时写「语气不明」，不要臆测」。宁可空着，
  也不让模型为了填满字段编造情绪，否则复盘节点会把编造的情绪当成证据。
- **可选字段**：`tone` 缺失不影响条目入库（解析器只做类型收敛），只是这条记录少一类线索。
- **契约与题面分开**：`DEFAULT_UNDERSTANDING_PROMPT` 是题面、`OUTPUT_FORMAT_INSTRUCTION` 是契约。
  使用者可以换题面，但契约不能换——解析器认的就是这套字段。

### 3.3 定级由程序兜底

模型只能看到转写文本，看不到「有多少片段没识别成功」。因此 `merge_reviews` 会按真实覆盖面
**下调**模型给出的等级：

| 条件 | 结果 |
| --- | --- |
| 识别成功片段占比 < 50% | 强制为「受限」，只给主题与结构的观察 |
| 有失败片段，模型给「完整」 | 降为「部分」 |
| 其余 | 采用模型定级 |

下调理由同时写入 `level_reason` 与 `missing_info`，让用户看到结论的边界在哪。

## 4. 复盘输入与长转写分批

### 4.1 输入渲染

`app/transcript.py` 的 `render_review_text` / `segment_records` 负责把逐片记录拼成复盘输入。它与已有的
人工核对全文（`render_text`）**刻意分开**，因为取向不同：

- 人工核对用的全文有片段分隔、解析告警括注、越界标记，便于逐条比对；
- 复盘输入是给模型的，同样内容带上这些标记只是噪声，token 却要照付。

复盘输入保留两样东西：**时间戳**（结论要能指出发生位置）与**语气标注**（分析表达方式的唯一线索）。
失败与未识别的片段以一行括注明确写出，否则模型会把「缺失」当成「这段时间没人说话」，
进而给出「内容空洞」这类错误结论。

### 4.2 分批与合并

一场两三小时的直播，转写可能超出单次请求的输入上限。`review_input_chars_per_call`（默认 20000 字）
是单批阈值，超出则按**记录边界**切批：一条语音记录是不能再分的最小单位，不会被劈成两半分送两批。

分批调用后的合并是**结构性**的，不发起第二次「摘要合并」调用：

- `key_events` 按时间去重排序；`top_issues` / `next_actions` 去重后按准则截断到 3 条（先到先得，
  提示词已要求模型按重要性排序）；
- `analysis_level` 取各批中最保守的一档；
- `one_line` 多批时给出「第 1 段 / 第 2 段」的分段概括，并注明本场是分批分析。

多调一次模型就多一处编造的机会，而合并规则本身是确定的，因此不交给模型做。

## 5. 执行与状态

复盘是**独立阶段**，与识别同构：写自己的一组 `review_*` 字段，不动任务的 `status`。
`submit(task_id, TASK_KIND_REVIEW)` 复用同一线程池与在途去重。

| 情形 | 处理 |
| --- | --- |
| 没有任何已识别的语音记录 | 判 `skipped`，**不发请求**，并说明「请先完成识别」 |
| 有失败片段 | **不阻断**：缺口数量进模型输入，也写入结论的等级与缺口清单 |
| 模型调用失败（单批即整场） | 判 `failed`，原因落库（服务端错误保留 `request_id`） |
| 进程重启打断 | `reclaim_interrupted_review` 退回 `pending` 并重新入队 |
| 重跑 | 结论**覆盖**，不留历史版本 |

两条刻意的选择：

- **失败片段不阻断**。「一片失败就出不了复盘」会让用户拿不到任何结论，而带着明确警示的结论
  仍然有用——只要它如实说明缺口在哪。这也是准则「素材不足应降低置信度，禁止硬凑」的落地方式。
- **重启后续跑而不问用户**。复盘的输入是已落库的识别结果，续跑最多重跑一次文本调用，
  不会触碰识别、不会重新计费视频理解，因此自动续跑是划算的。

## 6. 结果与呈现

| 层次 | 内容 | 位置 |
| --- | --- | --- |
| 状态与覆盖面 | 状态、进度、投入分析的语音条数、批次、模型、起止时间 | 任务接口 `review` |
| 结构化结论 | 一句话结论、分析等级与依据、关键事件、发现、TOP 问题、下一场动作、缺口清单 | 同上 `review.result` |
| Markdown 报告 | 与人机同源渲染的一份可下载报告 | `GET /api/tasks/{id}/review.md` |

界面新增第 4 块「复盘结论」，排在识别结果之后，对应处理链路的第四阶段：

- **汇总**：复盘状态、分析等级、投入分析的语音条数、批次、完成时间、模型。
- **结论正文**：定级依据在最前（先讲边界再讲结论）；关键事件按时间排列；每条发现带**证据等级标签**
  （事实 / 高置信推断 / 待验证假设）与时间码；TOP 问题给出证据、影响、根因与动作；下一场动作给出
  目标、做法与观察项；「本场不足以判断」单独成块并用提示色标出。
- **时间戳只作文本坐标**：视频切片播放已撤销，这里不做跳转，用户带着时间点去原始素材核对。

## 7. 范围与后续

本版**不做**：巨懂车经营数据接入、画面/OCR/主播行为识别、主播档案与跨场对比、100 分制评分、
事件与视频回看联动、复盘的多次结果对比。

「这份复盘结论是否有助于改进直播」这一条验收结论，需要在测试环境用真实整场直播跑完人工评估后给出；
本版把判断所需的数据（结构化结论、各批原始返回、token 用量、归一告警）都留档，使该结论有据可依。
