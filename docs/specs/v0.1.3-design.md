# V0.1.3 设计文档：视频上传与任务管理

> 本文是 V0.1.3（视频上传与任务管理）的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：`README.md`、`docs/specs/v0.1-plan.md` 第 4 节 V0.1.3、`docs/specs/v0.1.1-design.md`、`docs/specs/v0.1.2-design.md`、`docs/README.md` 文档规范。
> 定位：记录 V0.1.3 的选型决策、状态机与模块边界，不规定函数签名逐个参数、字段清单等实现细节；具体代码结构在实现中确定。

## 1. 目标

打通 1～2GB 大文件上传与后台任务记录，使原始视频可靠落入对象存储并建立可追踪的任务。本版以「上传 + 落存储 + 任务记录」为验收边界，不要求完成探测与切分。

## 2. 选型与决策

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 上传链路 | 前端分片 → 后端中转 → 合并 → 上传对象存储 | 进度与断点由后端掌握，状态可持久化、可查询；TOS 桶无需 CORS，跨域问题与凭据不下发浏览器 |
| 分片大小 | 后端下发固定值（默认 8MB，`UPLOAD_CHUNK_SIZE` 可配） | 前端不自行决定分片粒度；8MB 下 2GB 约 256 片，请求数可控 |
| 分片落盘 | `{MEDIA_ROOT}/chunks/{上传会话 id}/{序号:06d}.part` | 序号定长便于排序与缺片检测；按会话分目录便于整体清理 |
| 分片并发 | 前端同时 4 片 | 兼顾带宽利用与后端压力，顺序无关（后端只按序号落盘） |
| 续传范围 | 同一上传会话内续传（前端查询已收分片后跳过） | 不引入跨会话/跨重启的会话恢复，保持本版最小；刷新后可对同一会话补齐缺片 |
| 合并方式 | 按序号顺序拼接为临时文件，校验总字节数后整体上传 | 顺序拼接保证内容正确；大小校验拦截缺片与截断 |
| 临时文件清理 | 合并上传结束后 `finally` 清理分片目录与合并临时文件 | 失败也清理，避免测试环境磁盘被 2GB 级残留占满 |
| 数据模型 | 新增 `UploadSession` 与 `Task` 两张表 | 上传过程状态与业务任务生命周期分开，任务不因上传会话关闭而消失 |
| 建表方式 | 启动时 `create_all`，不引入 Alembic | V0 验证阶段表结构仍在演进，迁移工具收益低于其运维成本 |
| 后台执行 | 进程内 `ThreadPoolExecutor` + 认领式状态流转（`uploaded` → `processing`） | 单实例部署下最简可靠；认领用 token 判据，避免重复执行同一任务 |
| 进度呈现 | 前端轮询任务接口（上传期间约 1s，处理期间约 2s） | 实现简单、可断线重连，nginx 与 compose 无需改动；本版不要求秒级实时 |
| 任务体内容 | 空壳占位（仅状态流转与存储落地） | 探测属 V0.1.4、切分属 V0.1.5；本版只保证「关闭页面任务继续推进」 |
| 失败可见 | 失败原因写入任务与上传会话的错误字段，接口原样返回 | 验收要求「上传失败可查看原因并可重新发起」 |
| 重试方式 | `POST /api/tasks/{id}/retry` 重新入队；上传失败则重新发起新上传会话 | 任务重试复用已落存储的原始视频，无需重新上传 |

## 3. 模块边界

```
backend/app/
├─ models.py              # UploadSession、Task 的 SQLAlchemy 声明
├─ database.py            # 引擎/会话工厂 + init_db()（create_all）
├─ schemas.py             # 上传与任务接口的请求/响应模型（Pydantic）
├─ tasks/
│  ├─ __init__.py
│  ├─ executor.py         # 线程池执行器与入队接口
│  └─ runner.py           # 认领式状态流转与任务体（本版为空壳）
├─ routers/
│  ├─ uploads.py          # 创建会话、收分片、完成合并
│  └─ tasks.py            # 查询任务、重试任务
└─ storage/               # V0.1.2 既有，本版只调用其契约
```

依赖方向：`routers` → `tasks` / `storage` / `models`；`tasks` → `storage` / `models`；`storage` 不感知上传与任务。业务层只依赖 `ObjectStorage` 契约与 `get_storage()`。

### 3.1 状态机

**上传会话**：`uploading` → `assembling` → `completed`；任一环节失败转 `failed` 并记录原因。只有 `uploading` 状态接受分片，`completed` 后重复上传分片返回明确错误。

**任务**：`uploading` → `uploaded` → `processing` → `succeeded` / `failed`。`uploaded` 表示原始视频已落存储、等待处理；`processing` 由执行器认领后写入（含 `process_token`），避免重复执行；`failed` 可由 `retry` 退回 `uploaded` 重新入队。

### 3.2 接口职责

- `POST /api/uploads`：创建上传会话，返回会话 id、分片大小与**已收分片序号**，供前端跳过已完成分片。
- `PUT /api/uploads/{id}/chunks/{index}`：接收单分片原始字节，落盘后推进已收字节数；序号越界或会话状态不允许时返回明确错误。
- `POST /api/uploads/{id}/complete`：校验分片齐全 → 顺序合并 → 校验总大小 → 上传对象存储 `original/` → 建/更新任务并入队；缺片时返回缺失序号供前端补齐。
- `GET /api/tasks/{id}`：返回任务状态、进度、对象键、大小与失败原因。
- `POST /api/tasks/{id}/retry`：仅 `failed` 的任务可重试，重新入队。

接口前缀统一为 `/api`，与既有 `/health` 区分：`/health` 面向探针，`/api` 面向前端。

## 4. 配置与存储

### 4.1 配置扩展

`config.py` 新增：

- `media_root`：本地产物根目录（本地默认 `./media`，容器内 `/app/media`）。
- `upload_chunk_size`：分片大小（字节，默认 8MB），由后端下发，前端不硬编码。

存储继续沿用 `StorageBackend` 契约；原始视频以 `kind=original` 生成对象键，不新增 `kind`。

### 4.2 存储调用

合并完成后调用 `upload_file(local_path, object_key)`，对象键由 `generate_object_key(OBJECT_KIND_ORIGINAL, filename)` 生成。上传失败映射为任务失败并记录领域异常信息（服务端错误含 `request_id`），不吞异常。

## 5. 前端

- **上传页**：选择文件 → 创建会话 → 按后端下发分片大小切片并并发上传 → 显示上传进度 → 完成后轮询任务状态 → 展示「上传成功 / 处理中 / 已完成 / 失败（原因）」，失败提供重新上传与任务重试入口。
- **进度语义**：上传进度与任务进度分开呈现，避免把「上传完成」误读为「处理完成」。
- **轮询**：抽为独立 hook，卸载时取消；页面刷新后仍可通过任务列表/任务 id 继续查看状态。
- **任务列表**：展示历史任务与状态，可再次进入查看，替代「仅看当前一次上传」的临时状态。

**实现后的实际取舍**（与上面计划的差异）：

- 预览用的任务列表接口已实现（`GET /api/tasks`），但 V0.1.3 前端只呈现当前这次上传的任务；历史任务列表页放到 V0.1.6 的结果查看一起做，避免本版出现没有下文的空列表。
- 轮询触发器用「任务 id + 单调递增序号」而非任务 id 本身：失败后立即点重试时，任务 id 未变，仅靠 id 作依赖不会重启轮询，界面会停在中途状态。
- 页面用 hash 区分两屏（上传 / 服务状态），不引入路由依赖。

## 6. 错误处理与安全

- 上传与任务失败一律落库为明确原因，接口不返回堆栈；日志记录原因与服务端错误的 `request_id`。
- 分片请求的大小上限做校验，超过单片约定大小即拒绝，避免异常请求写满磁盘。
- 上传内容不进入仓库与镜像：`MEDIA_ROOT` 已由 `.gitignore` 与 `.dockerignore` 排除。
- 凭据约束沿用 V0.1.2：AK/SK 仅从环境变量读取，不入日志、不入仓库。

## 7. 测试

**本地（Mock 存储）**：

- 上传会话：创建、分片乱序与重复上传、缺片完成被拒并列出缺失序号、字节数不符被拒、完成后重复上传分片被拒。
- 合并与落存储：合并后对象存储中存在对应 `original/` 对象，大小与声明一致，临时文件与分片目录已清理。
- 任务：创建后状态为 `uploading`，上传完成后转 `uploaded`，执行器认领后转 `processing` 并最终 `succeeded`；注入存储故障时转 `failed` 且原因可见，`retry` 后可重新执行。
- 并发与幂等：重复认领不产生重复执行；同一任务多次重试不重复计费式副作用（本版以状态断言）。
- 既有 V0.1.1 / V0.1.2 测试全部回归通过。

**前端**：上传页在 idle → 上传中 → 已上传 → 处理中 → 成功、以及失败与重试两条路径上的渲染断言。

**测试环境**：真实 TS 录屏（1～2GB）分片上传 → 合并 → TOS `original/` 落盘可查；任务记录与对象键对应正确；上传中断后可补齐缺片完成；关闭页面后任务仍在后台推进。

## 8. 验收要点（对应 v0.1-plan.md 第 4 节 V0.1.3）

- 上传大文件成功，任务被创建且状态可见；关闭页面后任务仍在后台推进。
- 原始视频在 TOS 中可查（测试环境），任务记录与文件对应关系正确。
- 上传失败可查看原因并可重新发起。
- 本版本以「上传 + 落存储 + 任务记录」为验收边界，不要求完成切分。

**本地已完成的验证**（存储为 Mock）：

- 后端 98 项单测通过，覆盖分片乱序/重复/缺片/大小不符、失败保留分片、任务认领互斥、重试守卫、进程重启后重新入队。
- 前端 14 项用例通过，覆盖上传进度、缺片提示、失败原因、重试后继续轮询到成功、两屏切换。
- 真实启动 uvicorn 走通「创建会话 → 分片上传 → 合并入库 → 任务成功 → 列表可见」，并校验入库内容逐字节一致。

**仍需在测试环境验证**（本机无 Docker 与 TOS 凭据）：

- 真实 1～2GB TS 录屏经 nginx 代理上传到 TOS `original/` 落盘可查。
- 关闭页面后任务在容器内继续推进，重开页面可见最新状态。

## 9. 不在本版范围

- 媒体探测（V0.1.4）、预处理与切分（V0.1.5）、结果查看（V0.1.6）。
- 跨会话/跨重启的断点续传（后端保留同一次上传的分片，但前端刷新后不自动寻回原会话，需重新选择同一文件）、TOS 分片上传（multipart）优化、上传取消与配额管理。
- 上传取消与临时文件生命周期规则（当前仅服务端在入库成功或用户重传时清理）。
- 对象浏览页、任务删除与归档、多用户与鉴权。

> 任务删除已由补丁版本 V0.1.3.1 补齐，见 `docs/specs/v0.1.3.1-design.md`。
- 前端直传 TOS（需桶 CORS 与浏览器侧凭据暴露，本版不采用）。

## 10. 已知限制

- 本机未安装 Docker，compose 与 nginx 变更只做结构与语法自洽检查；上传链路与真实 TOS 落盘在测试环境验证。
- 后台执行器为进程内线程池，单实例部署下有效；进程重启时按 `uploaded` 状态重新入队，但多实例部署下的任务互斥不成立（认领逻辑是单库单实例语义）。
- 上传过程占用后端磁盘等于文件大小（分片 + 合并临时文件），峰值约为文件的 2 倍；测试环境需保证 `liverreview-media` 卷容量。
