# V0.5.2 设计文档：管理员账号模块

> 本文是 V0.5.2 的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：任务方本次的规划要求。
> 定位：记录本版的方案取舍与边界记账，不规定函数签名与字段清单（那些看代码即可）。

## 1. 本次范围

任务方给出的三条要求：

1. 左侧边栏新增「账号管理」模块，仅对 admin 管理员账号开放，普通账号不可见。
2. 「账号管理」支持新增、删除账号（不包括 admin 账号）。
3. 本版仍然不做数据隔离，所有账号共享一份数据。

顺序实现为三步：后端角色判定与账号接口 → 前端账号管理界面 → 文档与端到端验收。三步之间
只有一条硬依赖（前端调后端接口），因此边界清晰，没有可并行的分支。

## 2. 与 V0.5.1 的关系：把留好的伏笔接上

V0.5.1 在 `specs/v0.5.1-design.md` §4 的边界账本里记着两条，本版正是来兑现它们的：

| V0.5.1 记账 | 本次的变化 |
|---|---|
| `users.role` 列已落库（恒为 `admin`），但没有任何判定依赖它 | 新增 `ROLE_MEMBER`，`require_admin` 成为第一个读 role 的判定 |
| 「账号增删改的接口」不做，建号只能跑脚本 | 列出、新建、删除三个接口上线，普通账号的增删回到界面 |

`role` 列在 V0.5.1 就已带 `server_default` 落库，因此本次**不动表结构**，旧库启动即兼容。
账号的读写原语（`list_users` / `create_user` / `delete_user` / `delete_user_sessions`）也
在 V0.5.1 就备好了，本版只是把它们接到 HTTP 上。

## 3. 方案取舍

### 3.1 角色判定写成 `require_user` 的子依赖

`require_admin` 声明为 `Depends(require_user)`，而不是自己再解析一次 Cookie：

```python
def require_admin(current: CurrentUser = Depends(require_user)) -> CurrentUser:
    if current.role != ROLE_ADMIN:
        raise HTTPException(status_code=403, detail="只有管理员账号可以执行此操作")
    return current
```

FastAPI 会缓存同一请求内的依赖结果，因此同源校验与会话查库在一次请求里仍然只做一遍。
`require_admin` 也直接复用了 `require_user` 已经完成的登录校验，不必重写那条拒绝路径。

### 3.2 越权返回 403，而不是 401

调用者是**已登录**的合法用户，只是这件事不对他开放。回 401 会被前端的统一处理当成
「会话失效」而把人弹回登录页——而他重新登录后依然没有权限，形成死循环。这个区分在
`tests/auth/test_accounts.py` 里单独钉住。

### 3.3 新建账号的角色由服务端决定，请求体里没有这个字段

界面只提供建普通账号，接口就不该接受更大的权力。`AccountCreateRequest` 因此不含 `role`，
服务端写死 `ROLE_MEMBER`。**界面不是唯一的调用方**——留一个角色字段等于把提权路径开在
接口上，任何拿到管理员 Cookie 的人都能顺手造一个管理员。

要造第二个管理员仍走 `python -m app.auth.init_admin`（原有能力，未改动）。

### 3.4 删除保护按角色判定，不按用户名或 id

`init_admin --username` 可以建出任意名字的管理员账号，按用户名硬编码会漏掉它们；按 id
判定则只能护住第一个。因此判据是 `role == ROLE_ADMIN`：**所有管理员账号一律不可删**。

这条同时消除了「管理员删掉自己」的情形——既然没有任何管理员能被删掉，删自己这条路径
自然不存在，不需要再写一条自我删除的检查。

### 3.5 口令长度下限从脚本上提到 `password.py`

建号现在有两条路径（初始化脚本、界面接口），两边必须是同一条策略。原先
`MIN_PASSWORD_LENGTH` 定义在 `init_admin.py` 里，本版把它移到 `password.py`，两处共用——
否则会出现「命令行拦下的口令界面照收」这种前后不一致。

接口侧不用 pydantic 的 `Field(min_length=...)`：那返回 422 加一段英文校验说明，而本项目的
中文 `detail` 是直接展示给使用者的文案，两者不是同一种东西。

### 3.6 界面只是可见性收敛，边界仍在后端

侧栏入口按角色渲染，普通账号手敲 `#/accounts` 会看到一页权限说明而不是账号列表。这是
**体验**上的收敛：把一个注定 403 的入口露给没有权限的人，只会让他点进去撞一堵墙。

真正的边界是后端那一层依赖。删掉前端判断，接口该拒的仍然拒——`App.tsx` 的注释与
`AccountsPage.tsx` 的模块说明都写明了这一点，避免后来者把界面判断误当成安全措施。

### 3.7 账号管理页沿用现有的表单与表格约定

- 表单照 `LoginPage.tsx` 的范式：每个字段一个 `useState`、`pending` 标志防重复提交、失败
  走 `role="alert"` 的 `.field-notice`、失败后保留账号只清口令。
- 列表照 `ClipTable.tsx` 的表格约定（`.table-wrap` > `.table`，`scope="col"` 表头）。
- 角色用小圆点 + 文字（`.status`），不用彩色徽章——与项目里状态的处理方式一致。
- **不引入弹窗组件**：删除确认用 `window.confirm`，与任务删除处（`Workbench.tsx`）相同。
  本项目刻意没有 modal，为一个确认框引入第一个不划算。
- 管理员那一行不渲染删除按钮，而不是渲染一个按下必然失败的按钮。

### 3.8 角色随登录响应一起返回

`UserResponse` 加了 `role`，`/api/auth/login` 与 `/api/auth/session` 共用这个结构，因此前端
登录后立刻知道自己的角色，不需要再加一个「我是谁、我有什么权限」的查询接口。

把角色藏起来并不会更安全：它只决定界面的可见性，后端对每个管理接口都单独判角色。

## 4. 未做（边界记账）

- **用户隔离**：任务表不加 owner 列，所有账号共享同一份数据，与 V0.5 / V0.5.1 一致。这是
  本版明确的范围外事项，不是遗漏。
- **角色提权入口**：界面只能建普通账号。要造第二个管理员仍须在服务端执行脚本。
- **改口令界面**：仍然只有命令行。与 V0.5.1 的边界相同，本版未动。
- **停用 / 禁用账号**：只有硬删除。删了就没了，没有「暂时冻结」这个中间态。
- **在线设备查看与批量踢人**：`store.list_user_sessions` 已有查询能力，仍没有接口与界面。
- **细粒度权限**：只有「能不能管账号」这一件事被判定。上传、处理、复盘、下载对所有登录
  账号一视同仁，没有只读账号之类的中间档。
- **改自己的显示名**：账号管理页只能建与删，不能改。改显示名仍需直接改库。
- **登录失败审计**：仍然只有进程日志，与 V0.5.1 相同。

## 5. 验收标准

1. 管理员登录后侧栏出现「账号管理」，普通账号侧栏没有这一项。
2. 账号管理页能新增账号，新建出来的一律是普通账号（`role` 为 `member`）；账号重复、口令
   过短都给中文报错且不落库。
3. 能删除普通账号；被删账号已登录的会话立即失效，旧令牌再也换不到身份。
4. **管理员账号不可删除**，任一管理员账号走接口删除都返回 400；界面上这些行不显示删除按钮。
5. 普通账号调用三个账号接口一律 403（不是 401），未登录一律 401。
6. 响应体里不出现口令哈希。
7. 所有账号仍然共享同一套任务数据，普通账号能看到管理员上传的全部任务。

自动化覆盖：后端 `backend/tests/auth/test_accounts.py`（权限边界、建号角色、删号保护与会话
作废）与 `test_route_protection.py` 补的三条端点枚举；前端 `frontend/src/App.test.tsx` 新增
三条（管理员可见、普通账号不可见、手敲 hash 得到说明页）。

## 6. 测试环境待验（本机未覆盖）

本机不部署 Docker、也未跑真实容器与浏览器，以下需在测试环境完成：

- 用界面在真实浏览器里建一个普通账号，再用它在无痕窗口登录，确认能进工作台、看得到全部
  任务数据、侧栏没有「账号管理」。
- 确认反向代理下新增与删除两个写请求不被 CSRF 同源校验误判（V0.5.1 那次 403 就属于
  「本机测不到、容器里才暴露」的一类，写接口同样是写操作）。
