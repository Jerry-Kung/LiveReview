# V0.1 版本计划

> 本文是 V0.1（长视频处理与切分）的阶段性规划文档，属 `specs/` 下的开发任务期间产出。
> 依据：`README.md` 的 V0.1 定义、`docs/README.md` 的文档规范、`docs/tos_examples/` 的 TOS 接入说明。
> 定位：规划 V0.1 的拆解与验收节奏，不规定目录、类、接口、字段等实现细节；详细设计在开发阶段结合实际验证确定。

## 1. 背景与拆分原则

`README.md` 将 V0.1 定义为「长视频处理与切分」：接收 1～2GB 直播录屏，完成媒体探测、必要格式处理与分片切分，保存原始文件、切片及时间对应关系，提供处理进度与结果查看，不依赖模型识别即可独立验收。

V0.1 原始范围同时覆盖前端、后端、存储、媒体处理与任务调度，属于跨多模块的中大型任务。按「小步快跑」原则，将其拆分为多个**独立、可验证、逐级叠加**的小版本，版本号从 V0.1.1 开始递增。每个小版本满足：

- 可运行：产出可在对应环境启动的最小闭环。
- 可测试：有明确的单元或集成测试手段。
- 可独立验收：有独立的验收要点，不依赖后续版本。
- 可回归：不破坏已交付版本的既有能力。

## 2. 拆分总览

| 版本 | 主题 | 核心交付 | 主要验收环境 |
| --- | --- | --- | --- |
| V0.1.1 | 项目骨架与运行环境 | 前后端脚手架、测试环境、配置管理、健康检查 | 本地 + 测试环境 |
| V0.1.2 | TOS 对象存储接入 | 存储模块封装、上传/下载/删除/预签名 | 本地(Mock) + 测试环境 |

| V0.1.4 | 媒体探测 | ffprobe 元数据探测入库 | 测试环境 |
| V0.1.5 | 预处理与切分 | 格式处理、分片切分、时间映射、覆盖校验 | 测试环境 |
| V0.1.6 | 工作台前端界面 | 商务风界面重构、流程移植、V0.1 完整验收 | 本地 + 测试环境 |

## 3. 关键策略（贯穿全版本）

### 3.1 FFmpeg 部署分工

- **本地不部署 FFmpeg**。FFmpeg / ffprobe 仅安装在测试环境（Ubuntu 24.04）的 Docker Compose 包中。
- 所有涉及 FFmpeg 的**单元测试、集成测试与端到端测试统一在测试环境执行**，本地不运行。
- 本地开发仅验证不依赖 FFmpeg 的逻辑：任务流转、存储封装（Mock）、接口契约、前端交互。
- 媒体处理代码以「调用 ffmpeg/ffprobe 命令行」的方式实现，具体命令参数与验证以测试环境实测结果为准。

### 3.2 对象存储分工

- 使用火山引擎 TOS 存储**原始视频**与业务流程中产出的**中间视频文件（切片）**。
- 存储接入直接复用 `docs/tos_examples/` 的用法与封装要点：客户端单例、上传 + 预签名合并、object_key 唯一化、AK/SK 仅从环境变量读取。
- 本地开发用 Mock/桩替代真实 TOS，验证存储模块的业务逻辑与错误处理；真实上传/下载/删除与预签名连通性在测试环境验证。
- 对象存储只承担「存储与按需取回」，不改变任务结果与时间对应关系的正确性判断；本地无 TOS 凭据不影响除 V0.1.2 之外版本的本地开发。

### 3.3 测试素材

- 切片与端到端验证使用至少一场符合目标规模（1～2GB、TS 格式）的真实直播录屏，素材仅用于测试环境，不进仓库。
- 小文件样例（用于上传链路、任务流转等非媒体类测试）由开发阶段准备，控制在合理体积内。

### 3.4 环境分工矩阵

| 验证内容 | 本地 | 测试环境 |
| --- | --- | --- |
| 前端交互、页面渲染 | ✅ | ✅ |
| 后端接口契约、任务状态流转（不含 FFmpeg/TOS 真实调用） | ✅（Mock） | ✅ |
| TOS 真实上传/下载/删除、预签名 URL 有效性 | ❌ | ✅ |
| ffprobe 探测真实媒体文件 | ❌ | ✅ |
| 转封装/转码/切分真实素材 | ❌ | ✅ |
| 切片可播放、音画同步、时间映射正确性 | ❌ | ✅ |
| 端到端：上传 → 探测 → 切分 → 查看 | ❌ | ✅ |

## 4. 版本详情

### V0.1.1 项目骨架与运行环境

**目标**：确立可运行的最小骨架与开发/测试环境分工基线，为后续版本提供稳定底座。

**范围**：

- 建立前后端项目骨架（前端 TypeScript + React 系框架；后端 Python + FastAPI，具体选型由开发阶段确定并记录）。
- 建立 Docker Compose 测试环境骨架（Ubuntu 24.04），预留 FFmpeg 与后端/前端服务挂载点。
- 建立配置管理：环境差异（存储凭据、服务地址、媒体工具路径等）通过环境变量管理。
- 提供后端健康检查端点与前端可访问的基础页面。
- 明确本地与测试环境的运行、构建、测试命令入口。

**验收要点**：

- 前后端可在本地启动并访问；后端健康检查通过。
- 测试环境可通过 Docker Compose 拉起，后端健康检查通过。
- 配置文件约定清晰，敏感凭据（TOS AK/SK 等）仅从环境变量读取，不落库不落仓库。

**环境分工**：本地完成全部验收；测试环境验证 Docker Compose 可拉起。

### V0.1.2 TOS 对象存储接入

**目标**：落地统一的对象存储能力，作为原始视频与中间切片的存储底座。

**范围**：

- 基于 `docs/tos_examples/` 实现存储模块：初始化客户端、上传、下载、删除、生成预签名 URL，覆盖两类异常（客户端/服务端）处理与日志。
- 遵循封装要点：客户端单例、上传 + 预签名合并、object_key 唯一化。
- 提供存储模块的本地 Mock 实现，供其他版本本地开发与测试使用。

**验收要点**：

- 本地：通过 Mock 验证存储模块的业务逻辑、异常处理与 object_key 唯一性（单测覆盖）。
- 测试环境：使用真实 TOS 凭据完成一次小文件的上传 → 生成预签名 URL（可访问）→ 下载 → 删除的连通验证。
- AK/SK 不出现在代码、日志与仓库中；服务端异常的 request_id 记录进日志。

**环境分工**：逻辑与 Mock 测试在本地；真实连通验证在测试环境。

### V0.1.3 视频上传与任务管理

**目标**：打通大文件上传与后台任务记录，使原始视频可靠落入对象存储并建立可追踪的任务。

**范围**：

- 前端上传入口，适配 1～2GB 大文件（分片/断点策略由开发阶段按需确定）。
- 后端接收上传，建立处理任务，维护任务状态与进度（已提交、处理中、成功、失败等）。
- 原始视频上传完成后落 TOS，并保存任务与文件对应关系。
- 关闭页面不影响后台任务继续执行。

**验收要点**：

- 上传大文件成功，任务被创建且状态可见；关闭页面后任务仍在后台推进。
- 原始视频在 TOS 中可查（测试环境），任务记录与文件对应关系正确。
- 上传失败可查看原因并可重新发起。
- 本版本以「上传 + 落存储 + 任务记录」为验收边界，不要求完成切分。

**环境分工**：本地以 Mock 验证上传与任务流转逻辑；测试环境验证真实 TOS 落盘与大文件上传链路。

### V0.1.4 媒体探测

**目标**：在测试环境接入 ffprobe，为后续切分提供可靠的媒体元数据。

**范围**：

- 在测试环境接入 ffprobe，对上传的原始视频执行媒体探测，产出格式、时长、分辨率、编码、码率、音视频流等元数据。
- 探测结果保存并与任务、文件关联。
- 对探测失败、异常媒体状态给出明确失败信息，支持重新探测。

**验收要点**：

- 使用真实 TS 录屏完成探测，元数据字段与实际媒体一致（时长、分辨率、编码等抽查核对）。
- 探测异常时能定位原因并支持重试。
- 探测结果可供后续切分直接使用（时间对应关系以探测得到的时间基准为准）。

**环境分工**：全部在测试环境执行；本地仅以 Mock 验证元数据入库与状态流转逻辑。

### V0.1.5 预处理与切分

**目标**：将完整直播录屏处理为可用的短片段，形成切片与时间对应关系，这是 V0.1 的核心交付。

**范围**：

- 根据探测结果决定处理方式：可直接使用的格式保留原样，需要时进行重新封装或转码，确保音画同步可用。
- 采用几分钟级片段作为初始切分方向，片长与重叠范围按模型限制、内容密度与实测效果调整。
- 生成切片，并保存每片在原视频中的起止时间、覆盖关系（含预期重叠）与缺失信息。
- 切片文件落 TOS；切分完成后做整场覆盖校验（交界、重叠、缺失可检查）。
- 切分失败可查看原因并支持局部/整体重新执行。

**验收要点**：

- 使用至少一场符合目标规模的真实 TS 录屏完成整场切分。
- 切片可正常播放、保留声音与画面，可定位其在原视频中的时间范围。
- 切片覆盖整场视频；片段交界、预期重叠与异常缺失可检查。
- 已完成切片可供后续版本复用，无需重新上传原视频。

**环境分工**：全部在测试环境执行；本地仅以 Mock 验证切分任务的编排与状态流转逻辑。

### V0.1.6 工作台前端界面

**目标**：为项目建立一套完整的商务风前端界面，并把「上传 → 探测 → 切分 → 查看」流程移植到新界面上跑通。

**范围**（本次任务方对原定义的调整见 `v0.1.6-design.md` 第 1 节）：

- 界面重构：页眉（项目中文名称、用户区、服务状态）、侧栏（新建任务入口与历史记录）、主工作区。
- 上传、任务进度、探测结论、切分结论与切片列表迁移到新界面，链路与接口契约不变。
- 切片结果仅以文字信息呈现（序号、原视频时间范围、时长、体积、处理状态）；**撤销原定的切片回看**，主页不展示视频、不提供播放/回看入口。
- 预置功能区：用户登录（登录态仅前端，不请求后端）与历史记录（读既有任务列表接口，账号隔离待登录接入）。
- 处理进度与失败信息可视化，失败任务可重新执行。

**验收要点**：

- 页眉显示项目中文名称，预置用户登录组件与历史记录区域。
- 在测试环境跑通「上传 → 探测 → 切分 → 查看」完整流程，且在新界面上完成。
- 用户可从切片列表定位到任意切片在原视频中的时间范围（时间范围与位置条）。
- 关闭页面不影响后台处理；处理失败可查看原因并重新执行。
- 全部满足 `README.md` V0.1 的验收要点。

**环境分工**：界面与交互在本地与测试环境均可验证；端到端流程在测试环境验证。

## 5. 验收与回归节奏

- 每个版本以实际运行结果验收，不以文档或模块数量替代交付。
- 每版合并前回归上一版核心功能，避免回退。
- 失败场景可定位：任务/切片/探测的失败原因可见，可局部重试，已完成产物可复用。
- 版本顺序原则上线性推进；若某版依赖外部条件（如 TOS 凭据、测试素材）暂不具备，可在记录阻塞原因后先推进不依赖该项的版本，不阻塞整体节奏。

## 6. 明确不在 V0.1 范围

- 不接入任何模型识别（语音、画面、文字），识别属 V0.2。
- 不做内容整理、时间线语义化、复盘分析（V0.3、V0.4）。
- 不做实时直播监听、平台自动抓取、多场对比等（`README.md` 第 7 节边界内）。
