# V0.5.1 设计文档：账号与会话入库

> 本文是 V0.5.1 的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：任务方本次的规划要求。
> 定位：记录本版的方案取舍与边界记账，不规定函数签名与字段清单（那些看代码即可）。

## 1. 本次范围

任务方给出的四条要求：

1. 设计完善的 user-password 登录机制，账号与口令入库，不放配置文件。
2. 数据库设 `users` 表保存账号数据。
3. 后端用 session 机制管理登录信息，数据库设 `sessions` 表。
4. 提供一个初始化脚本用于冷启动创建 admin 账号，交互形态：

      管理员用户名：admin
      管理员密码：********
      再次输入密码：********
      管理员创建成功

顺序实现为四步：数据层 → 鉴权层改造 → 接口与脚本 → 测试与文档。四步之间没有可并行的
分支：接口依赖鉴权层提供的依赖，鉴权层依赖数据层的两张表。

## 2. 与 V0.5 的关系：不是推翻，是需求变了

V0.5 明确选了「签名 Cookie + 服务端不存任何东西」，并在 `specs/v0.5-design.md` §4 把代价
记在账上：**无法单独踢掉一个用户**，要立刻作废已签发的票据只能更换 `AUTH_SESSION_SECRET`，
代价是全员重登。本次要求的三件事，本质上是把那份账上记着的短板补掉：

| V0.5 的取舍 | 本次的变化 |
|---|---|
| 账号写在 `AUTH_USERS` 环境变量 | 账号入 `users` 表，数据库成为唯一来源 |
| 会话是自包含的签名票据 | 会话入 `sessions` 表，令牌本身只是随机串 |
| 踢人只能换密钥（全员重登） | 按会话或按账号精确撤销 |
| 改口令后旧票据仍然有效 | 改口令即作废该账号的旧会话 |
| 「重启会掉线」是一类需要告警的隐患 | 该隐患随签名密钥一起消失 |

V0.5 选无状态的理由（避开过期清理与并发写）当时是成立的，只是那时的需求里没有
「撤销」这一项。需求一变，无状态的代价就从「可接受」变成了「挡路」。

## 3. 方案取舍

### 3.1 令牌不再是签名票据，而是一串随机字符

令牌用 `secrets.token_urlsafe(32)` 生成（256 位熵），**服务端只存 SHA-256 摘要**，
Cookie 里放明文令牌。安全边界从「验签能否通过」变成「库里能否查到这一行」。

- 摘要是为了防「拿到数据库文件就能冒充任何人」。摘要不加盐、不用 PBKDF2：令牌是高熵
  随机串，没有字典可猜，慢哈希只会让每个请求多花几十毫秒而换不到实际强度。
- 留着 V0.5 的签名只会叠一层无用功——真正的有效性判定已经落在数据库上了，
  签名再对也不能让一行不存在的会话变得可用。

**Cookie 的形态一个字没改**：仍然是 `HttpOnly` + `SameSite=Lax`，仍然由
`AUTH_COOKIE_SECURE` 控制是否只在 HTTPS 下发送。前端 `session.ts` 因此完全不必改动，
接口契约（`POST /login`、`POST /logout`、`GET /session` 与它们的响应体）也保持原样。

### 3.2 每次请求查一次库，接受这个代价

`require_user` 现在每个请求都要读一次 `sessions`（主键命中）并带出 `users`。V0.5 的签名
票据不需要这一步。这是把会话收进数据库的直接成本，在这个量级（单实例、个位数账号、
SQLite）不构成瓶颈，换来的是撤销能力。

滑动续期的**写入**做了节流：只有剩余时间不足半个窗口时才更新 `expires_at`。不节流的话，
一次页面加载（任务轮询、分片上传、列表刷新）会变成几十次 UPDATE，而把窗口顺延几秒
并没有意义。

### 3.3 有效期分两段：滑动窗口 + 绝对上限

- `expires_at`：每次访问顺延一个窗口（默认 12 小时）。
- `absolute_expires_at`：从签发起算的硬上限（默认 7 天），续期不得越过。

只有滑动没有上限，等于一次登录永久有效；只有上限没有滑动，连续工作一整天会被中途
要求重新登录。两者都要，缺一不可。

### 3.4 撤销的粒度：按会话，也按账号

- 退出登录 → 删掉这一张会话。**与 V0.5 的关键差别**：旧令牌即便已被抄走也再无用处，
  而那时「登出」只对当前这台设备成立。
- 改口令、删账号 → 清掉该账号的全部会话。改口令而旧登录态继续有效是说不通的。
- 删账号同时靠外键级联清掉会话，不留指向空账号的活会话。

### 3.5 过期会话的清理：撞上即删 + 启动扫一遍

`resolve_session` 命中一张已过期的会话时顺手删掉它。剩下的（用户登录一次就再没回来）
在服务启动时由 `purge_expired_sessions` 扫一遍。本版用户数与登录频率都极低，不需要
定时任务；真需要时再加，接口形态不必变。

### 3.6 失败模式从「配置写错」变成「部署没做完」

V0.5 里一个账号都没有意味着 `AUTH_USERS` 没配（配置问题，500）。现在空库是冷启动的
正常状态，因此登录接口返回 **503 并明确写出 `python -m app.auth.init_admin`**。
这条文案很重要：不写清楚的话，空库的表现是「什么口令都不对」，使用者只会反复怀疑
自己记错了密码。

登录失败对外仍然只有一句「账号或密码不正确」，节流仍是进程内计数（理由同 V0.5）。

### 3.7 口令继续用标准库 PBKDF2，哈希继续自描述

`pbkdf2_sha256$迭代$盐$哈希` 这个格式不变，迭代次数仍取 24 万。只是存储位置从环境变量
变成 `users.password_hash`。不引 `passlib` / `bcrypt` 的理由同 V0.5：本阶段用不到
强度校验与多格式兼容。

### 3.8 初始化脚本的行为边界

- **口令不回显**（`getpass`），两次不一致即中止，退出码非 0。
- **账号已存在时不静默覆盖**：那等于给了一条顺手改掉别人口令的路径。此时说明情况并
  单独再问一次，答 y 才重设口令；`--force` 跳过确认供脚本使用。重设口令会一并作废
  该账号的旧会话，并在输出里说出来。
- **脚本自己建表**：冷启动时数据库可能是空的，脚本不该要求使用者先启动一次服务。
- `--list` 供运维查看已有账号，输出不含明文口令与哈希。
- 非交互模式（`--username/--password/--display-name`）供测试环境与自动化使用；
  `--password` 走命令行会被 shell 历史记录，因此在帮助文本里注明。

## 4. 未做（边界记账）

- **改口令的界面入口**：本版只有命令行（初始化脚本的重设路径）。登录后想改口令仍须
  在服务端执行脚本。做界面需要新增接口 + 前端表单，本版不做。
- **账号增删改的接口**：只有 `init_admin` 的建号与重设，没有删号、停用、改显示名的接口，
  这些仍需直接在数据库上操作或后续补脚本。
- **角色与权限**：`users.role` 列已落库（V0.5.1 恒为 `admin`），但没有任何判定依赖它，
  所有登录用户仍然等价。
- **用户隔离**：任务数据不按账号切分，与 V0.5 一致。数据库里依然没有记录「谁上传的」，
  将来要做隔离必须补列并在写入时带上。
- **在线设备查看与批量踢人**：`store.list_user_sessions` 已提供查询能力，但没有接口，
  也没有界面。
- **登录失败审计**：仍然只有进程日志，没有可查询的记录。
- **改口令时的会话保留**：`delete_user_sessions(keep=...)` 已支持「只清其他设备」，
  但本版没有调用点（没有改口令接口，自然也没有「当前这台」的概念）。
- **会话数量上限**：同一账号可以开任意多张会话，没有限制。
- **多实例部署**：节流仍在进程内存里，会话表虽是共享的但节流不是。

## 5. 验收标准

1. 账号在 `users` 表里，`AUTH_USERS` / `AUTH_SESSION_SECRET` 两个环境变量已从代码与
   配置样例中移除；不配置它们不影响启动，也不再有相关告警。
2. `python -m app.auth.init_admin` 按文档的提示顺序完成建号，产出可直接登录的 admin；
   账号重复、两次口令不一致、口令过短都给出明确报错且退出码非 0。
3. 登录成功在 `sessions` 表留下一条记录（库里只有摘要，没有明文令牌）；未登录、令牌
   伪造、会话过期、账号被删一律 401。
4. 退出登录后服务端那一行被真的删除，拿着旧令牌再来拿不到身份。
5. 同一账号的两张会话互不影响：退出其中一台，另一台仍然可用。
6. 改口令或删账号后该账号的旧会话立即失效。
7. 会话在滑动窗口内每次访问顺延，但不超过 7 天的绝对上限；剩余时间充裕时不写库。
8. 前端登录流程不需要任何改动即可照常工作（接口契约与 Cookie 属性均未变）。

自动化覆盖见 `backend/tests/auth/` 四组：`test_foundation.py`（口令、账号、会话的地基
单测）、`test_routes.py`（HTTP 契约与撤销行为）、`test_route_protection.py`（全部业务
端点未登录一律 401）、`test_cli.py`（初始化脚本）。前端沿用 `frontend/src/App.test.tsx`
的登录门槛一组，本版未新增前端测试（前端代码未改）。

## 6. 测试环境待验（本机未覆盖）

本机不部署 Docker、也未跑真实容器，以下需在测试环境完成：

- 容器内执行初始化脚本建号，并在浏览器完成一次真实登录。
- 删掉 `AUTH_USERS` / `AUTH_SESSION_SECRET` 后容器启动无相关告警。
- 数据卷里的 `liverreview.db` 从 V0.5 版本升级启动时自动建出两张新表（旧库里的数据
  不受影响），并确认此时登录返回 503 而非 500。

## 7. 测试环境实测反馈

第一次真实登录即暴露出一处本机测不到的故障，已修复（见 `changelog.md` 同日条目）：

- **反向代理下写请求被判成跨站**。同源校验在 V0.5 就写好了，本机测试用的是
  `TestClient`，它的 `Host` 本就不带端口，因此「带端口的 Origin 与不带端口的 Host」
  这一对组合从未被覆盖过；容器里 nginx 转发 `$host` 恰好制造了这一对组合。修法是
  nginx 转发 `$http_host` 加后端认 `X-Forwarded-Host`、并对不带端口的 Host 按同源放行，
  同时在 `tests/auth/test_routes.py` 补上这四种组合的用例。

**教训**：涉及「请求是从哪个地址来的」这类判定，本机测试环境与真实部署的差异不在业务
逻辑上，而在代理与浏览器实际发出的报文上；这类判定要在容器里真跑一次才算验过。
