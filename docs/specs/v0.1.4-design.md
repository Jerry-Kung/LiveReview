# V0.1.4 设计文档：媒体探测

> 本文是 V0.1.4（媒体探测）的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：`README.md`、`docs/specs/v0.1-plan.md` 第 4 节 V0.1.4、`docs/specs/v0.1.3-design.md`、`docs/README.md` 文档规范。
> 定位：记录 V0.1.4 的选型决策、探测对象来源与模块边界，不规定函数签名逐个参数、字段清单等实现细节。

## 1. 目标

在测试环境接入 ffprobe，对上传完成的原始视频执行媒体探测，产出格式、时长、分辨率、编码、码率、音视频流等元数据并与任务关联；探测失败给出明确原因、支持重试；探测得到的时间基准供 V0.1.5 切分直接使用。

## 2. 选型与决策

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 探测对象来源 | 使用上传链路的**本地副本**（`{MEDIA_ROOT}/originals/{任务 id}{后缀}`） | 上传后本地已有一份完整文件，直接喂给 ffprobe 省一次 GB 级网络往返，也避免对象存储的瞬时故障被误判为「媒体文件有问题」 |
| 副本保存时机 | 合并产物在入库成功后**移动到** `originals/`，而不是删除 | `assembling/` 是合并临时文件，语义上应释放；`originals/` 是待探测的输入，按任务 id 命名便于定位与清理 |
| 副本生命周期 | 探测成功即删除；探测失败保留 | 成功后不再需要（V0.1.5 用待定策略取回原视频），删除避免测试环境磁盘被多场 2GB 文件占满；失败保留便于在容器内直接复跑 ffprobe 定位 |
| 重试时副本缺失 | 从对象存储按对象键下载回同一路径再探测 | 使「首次执行」与「重试」共用同一段探测代码，不必为两种来源写两条分支 |
| ffprobe 调用 | `-v error -print_format json -show_format -show_streams -count_packets` | 结构化输出便于入库与幂等解析；`-count_packets` 让 TS 录屏（容器头 duration 常为 `N/A`）也能拿到可信时长，V0.1.5 的时间映射依赖该值 |
| 调用实现 | `subprocess.run` 传参数列表 + 超时 + 输出长度上限 | 不经 shell，避免文件名与路径被解释；超时与非零退出码映射为领域异常 `ProbeError`，原因落库 |
| 解析与调用分层 | `ffprobe.py` 纯解析（stdout → 结构化结果）与 `probe.py` 子进程调用分开 | 解析逻辑可在本地用固定 JSON 充分测试，不依赖本机安装 ffprobe |
| 元数据落库 | 常用字段升为 `Task` 的列；完整 ffprobe JSON 存 `metadata_json` | 验收要核对与实际媒体一致、V0.1.5 要直接取用，消费方不应解析 JSON；一对一关系不单开 `media_metadata` 表，避免为一个无多版本需求的从表增加复杂度 |
| 内容指纹 | 探测时对本地副本计算 sha256 存 `content_hash` | 与验收的「抽查核对」配合可证明「探测的到底是哪个文件」；顺带为后续判断同一素材复用留线索 |
| 任务种类 | 沿用 `Task(kind="ingest")`，`runner._process` 由空壳改为探测实现 | 本版仍是一次上传对应一次处理，不为单一处理步骤引入多种 kind |
| 进度语义 | 认领 0 → 探测中 20 → 入库完成 100 | 探测是单一不可切分的步骤，粗粒度进度即可满足「处理中可见」 |
| 失败与重试 | 失败原因写入 `Task.error`，复用既有 `POST /api/tasks/{id}/retry` | 已有接口的状态守卫与入队逻辑完全适用，无需新增重试入口 |
| 接口契约 | `TaskResponse` 增加嵌套 `metadata` 对象，字段缺失时为 null | 前端只读展示，不改变轮询与删除逻辑；嵌套可避免元数据字段与任务状态字段混杂在同一层 |
| 前端展示 | 任务成功后展示时长、分辨率、音视频编码；失败沿用既有 `error` 通路 | 本版不做结果页（属 V0.1.6），仅让探测结论可见可核对 |

## 3. 模块边界

```
backend/app/
├─ media/                 # 本版新增
│  ├─ __init__.py         # 对外导出 ProbeError、probe_media()
│  ├─ ffprobe.py          # 纯函数：ffprobe 的 JSON 输出 → 结构化元数据
│  ├─ probe.py            # 子进程调用、超时与错误映射
│  └─ cli.py              # 容器内定位用：python -m app.media.cli <文件路径|任务 id>
├─ config.py              # 探测配置项（工具路径、超时、输出上限）
├─ models.py              # Task 增加探测字段与 metadata_json
├─ schemas.py             # TaskMetadataResponse、TaskResponse.metadata
├─ tasks/runner.py        # 任务体由空壳改为：准备本地副本 → 探测 → 入库 → 清理副本
├─ deletion.py            # 删除任务时一并清理 originals/ 下的副本
└─ routers/               # 只透出 metadata，本版不新增路由
```

依赖方向：`tasks` → `media` / `storage` / `models`；`media` 只依赖配置与标准库，不感知数据库、HTTP 与对象存储；`storage` 不感知探测。本地副本的路径规则集中在 `app/media/locator.py` 式的单一入口（实际实现为 `app/media/paths.py`），避免路径拼装散落在路由与任务体两处。

### 3.1 状态机延伸

任务状态机不变（`uploading` → `uploaded` → `processing` → `succeeded` / `failed`），本版只填充 `processing` 内的任务体：

1. 认领任务，`progress=0`。
2. 准备本地副本：`originals/` 下存在则直接用；不存在则按 `object_key` 从对象存储下载到该路径。
3. ffprobe 探测 + 计算 sha256，`progress=20`。
4. 元数据写入任务行。
5. 删除本地副本，`progress=100`，状态转 `succeeded`。

任一步骤失败：状态转 `failed`，原因写入 `Task.error`，**本地副本保留**（若已下载），`retry` 可重新入队。

### 3.2 与上传链路的衔接

上传完成接口 `POST /api/uploads/{id}/complete` 的行为变化只有一处：合并产物不再 `cleanup_merged` 删除，而是在对象入库成功后移动到 `originals/{任务 id}{后缀}`。失败路径仍然保留分片与清理合并临时文件，与 V0.1.3 的约定一致。

### 3.3 实现中补上的两处

- **中断任务的回收**：进程被杀时任务会停在 `processing`，而认领凭据（`process_token`）是内存态的，重启后既无法重新认领也不会被 `requeue_pending` 入队，任务永久卡住。启动时增加 `reclaim_stale_processing()`，把这类任务退回 `uploaded` 再入队。探测是首个长耗时任务体，这个缺口从「只是理论问题」变成「跑一次真素材就会遇到」。
- **重试前清空元数据**：任务体的第一次 `db.commit()` 发生在元数据写完时，因此正常情况下「失败」与「有元数据」互斥；但重试接口会复用同一行，若上一次已写入部分结果，界面会残留陈旧结论。重试时一并清空探测字段，让「有元数据」等价于「本次探测成功」。

## 4. 配置

`config.py` 在既有 `ffmpeg_path` / `ffprobe_path` 基础上新增：

- `probe_timeout_seconds`：单次探测的超时（默认 300 秒）。1～2GB 的 TS 配 `-count_packets` 需要完整读一遍文件，超时留足余量。
- `probe_max_output_bytes`：stdout 长度上限（默认 8MB），拦截异常输入导致的输出膨胀。

`ffprobe_path` 由 `str` 放宽为 `str | list[str]`：既可以是容器内的可执行文件名，也可以是「解释器 + 脚本」形式，后者让本地测试用假 ffprobe 脚本替换真实工具，从而在未安装 FFmpeg 的机器上覆盖完整探测链路。

`FFMPEG_PATH` 本版仍不使用（转码与切分属 V0.1.5），保留占位。

## 5. 前端

- 任务成功后展示探测结论：时长、分辨率、音视频编码；字段缺失时显示「—」，不臆造取值。
- 探测失败展示失败原因，与上传失败的呈现走同一处（`Task.error`），失败时提供既有「重新执行任务」入口。
- 不做结果页、时间线与切片回看（属 V0.1.6）。

## 6. 错误处理与安全

- 探测失败原因分三类并原样落库：ffprobe 缺失/不可执行、超时、ffprobe 报错（含 stderr 摘要）、输出无法解析。
- 错误信息不包含完整命令行与文件绝对路径之外的敏感内容；对象存储异常的 `request_id` 仍按 V0.1.2 约定保留。
- 远端无内容可探测（无音视频流）视为失败，而不是写入空元数据。
- 本地副本与分片一样不入仓库与镜像（`MEDIA_ROOT` 已由 `.gitignore` / `.dockerignore` 排除）。

## 7. 测试

**本地（Mock 存储 + 假 ffprobe）**：

- `ffprobe.py` 解析：正常输出、流字段缺失、无音频流、无视频流、duration 为 `N/A` 时回退到包计数、非 JSON 输出报错。
- `probe.py` 调用：参数列表不含 shell、非零退出码带 stderr 摘要、超时映射为 `ProbeError`、ffprobe 不存在时的明确提示（POSIX 下用临时假脚本，Windows 下跳过真实执行类用例）。
- 任务链路：探测成功入库并清理副本、探测失败入库且副本保留、副本缺失时先下载再探测、下载失败映射为明确原因、`retry` 后二次探测成功。
- 删除链路：删除任务时 `originals/` 下副本一并清理。
- 既有 V0.1.1～V0.1.3 测试全部回归通过。

**前端**：任务成功后渲染元数据、字段缺失渲染占位、探测失败渲染失败原因。

**测试环境**：真实 TS 录屏（1～2GB）上传 → 探测，抽查时长、分辨率、编码与实际一致；用 `python -m app.media.cli` 对同一文件交叉核对；构造损坏文件验证失败原因可见且可重试。

## 8. 验收要点（对应 `v0.1-plan.md` 第 4 节 V0.1.4）

- 使用真实 TS 录屏完成探测，元数据字段与实际媒体一致（时长、分辨率、编码等抽查核对）。
- 探测异常时能定位原因并支持重试。
- 探测结果可供后续切分直接使用（时间对应关系以探测得到的时间基准为准）。

**本地已完成的验证**（存储为 Mock，ffprobe 用 `tests/fake_ffprobe.py` 替代）：

- 后端 153 项单测通过、8 项 POSIX 专属用例跳过（本机 Windows 无法直接执行脚本）。
- 覆盖：ffprobe 输出解析（含 duration 为 `N/A` 时回退包计数、字段缺失为 null、无音视频流判定）、调用层错误映射（退出码、超时、输出超限、可执行文件缺失）、探测入库与内容 sha256、探测成功清理副本、探测失败保留副本、副本缺失时回下载、重试清空陈旧元数据、进程重启回收 `processing` 任务、删除链路清理副本。
- 真实启动 uvicorn 走通「创建会话 → 分片上传 → 合并入库 → 探测入库 → 任务成功」，并逐字节校验元数据中的 `content_hash` 与上传内容一致。
- 前端 21 项用例通过，新增探测结论渲染、字段缺失占位、未探测不展示、探测失败展示原因与重试入口。

**仍需在测试环境验证**（本机无 Docker 与真实 ffprobe）：

- 真实 TS 录屏（1～2GB）的探测耗时与 `PROBE_TIMEOUT_SECONDS` 是否合适。
- 元数据与实际媒体逐项抽查一致（时长、分辨率、编码、帧率）。
- 损坏素材的失败原因是否足以定位，以及 `python -m app.media.cli` 的输出可用性。

## 9. 不在本版范围

- 格式转换、转码与分片切分（V0.1.5）、结果页与时间线（V0.1.6）。
- 探测结果的多次版本留存与历史对比；探测结果的编辑与人工修正。
- 多任务并行探测的限流与优先级（沿用既有线程池配置）。
- 对象存储侧的媒体元数据提取（不依赖云端能力，保持探测过程可控可复现）。

## 10. 已知限制

- 本机（Windows）未安装 ffprobe，子进程调用层的真实行为只在测试环境验证；本地以假脚本覆盖调用与错误映射逻辑。
- 本版未把 `-count_packets` 换成分片抽样策略：极长录屏的探测耗时约等于完整读一遍文件，若实测过慢，V0.1.5 再评估按需降级。
- 本地副本在探测期间额外占用一份等量磁盘（与上传分片同时存在时峰值约为文件的 3 倍），测试环境需保证 `liverreview-media` 卷容量。
- 表结构新增字段后，测试环境必须重建 SQLite 文件（`create_all` 不改已存在的表），见 `docs/runbooks/deployment.md`。
