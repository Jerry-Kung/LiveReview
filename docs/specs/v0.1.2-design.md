# V0.1.2 设计文档：TOS 对象存储接入

> 本文是 V0.1.2（TOS 对象存储接入）的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：`README.md`、`docs/specs/v0.1-plan.md` 第 4 节 V0.1.2、`docs/specs/v0.1.1-design.md`、`docs/tos_examples/`、`docs/README.md` 文档规范。
> 定位：记录 V0.1.2 的选型决策、模块边界与开发约定，不规定函数签名逐个参数、字段清单等实现细节；具体代码结构在实现计划中确定。

## 1. 目标

落地统一的对象存储能力，作为原始视频（V0.1.3）与中间切片（V0.1.5）的存储底座。本版交付存储模块本身与两条验证路径：本地 Mock 单测、测试环境真实 TOS 连通自检。不实现上传接口、任务管理与媒体处理。

## 2. 选型与决策

| 项 | 决策 | 理由 |
| --- | --- | --- |
| SDK | 火山引擎官方 `tos`（`>=2.6.0`），作为标准依赖 | `docs/tos_examples/` 即以官方 SDK 为准；标准依赖便于测试环境直接可用 |
| 模块位置 | `backend/app/storage/` | 存储是业务底座而非零散工具，独立顶层包，避免 `app/tools/storage/` 的多余嵌套 |
| 抽象方式 | 自定义 `ObjectStorage` 契约（协议类）+ 两个实现 | 本地无凭据、无 Docker，必须有 Mock 实现；契约让 V0.1.3～V0.1.6 面向接口编写 |
| 实现选择 | `get_storage()` 工厂 + 进程内单例，按 `STORAGE_BACKEND` 切换 | 与 V0.1.1 的 `get_settings()` 风格一致；`TosClientV2` 线程安全，单例即复用 |
| 客户端初始化 | 延迟初始化 + `threading.Lock` 保护 | 不在导入期建立连接；避免 V0.1.3 起后台任务并发下重复初始化 |
| object_key | 按用途分层：`{前缀}{kind}/{文件名主体}_{毫秒时间戳}_{uuid8}{扩展名}` | 原始视频与切片分目录，避免同名覆盖；唯一性靠时间戳 + 短 uuid 兜底 |
| 异常 | 统一映射为 `StorageError` 派生，服务端错误保留 `code`/`request_id`/`status_code` | 上层不必 import `tos`；`request_id` 是向火山引擎定位问题的唯一凭据 |
| 凭据安全 | 只从环境变量读取；AK/SK 与预签名 URL 均不进日志 | `v0.1-plan.md` 验收要点明确要求 |
| 连通验证 | 项目内自检命令 `python -m app.storage.verify` | 可在后端容器内直接执行；不污染单测；可重复用于后续版本回归 |
| 前端 | 仅状态指示（`/health` 增加 `storage` 字段，状态页补一行） | V0.1.2 验收要点均为后端与连通性；上传入口属 V0.1.3，不提前实现 |

## 3. 模块边界

```
backend/app/storage/
├─ __init__.py      # 导出契约与 get_storage() 工厂（其他版本唯一入口）
├─ base.py          # ObjectStorage 契约、StoredObject、StorageError 体系、异常映射辅助
├─ tos_backend.py   # TosStorage：官方 SDK 实现，对象内部延迟 import tos
├─ mock.py          # InMemoryStorage：本地内存实现，支持故障注入与固定时钟
└─ verify.py        # 真实 TOS 连通自检命令
```

依赖方向单向：`tos_backend` / `mock` → `base`；`__init__` 依据配置选择实现。业务层（V0.1.3 起）只依赖 `ObjectStorage` 与 `get_storage()`，不接触 `tos` SDK。

### 3.1 契约职责

`ObjectStorage` 覆盖 V0.1 所需的全部对象操作：

- **上传**：本地文件 → 对象，返回可入库的定位信息。
- **下载**：对象 → 本地文件（供 V0.1.5 复用已上传原视频，避免重复上传）。
- **读取字节**：对象 → `bytes`，供自检与后续小对象场景。
- **删除**：按对象键删除。
- **预签名 URL**：生成带有效期的下载链接。
- **对象键生成**：`generate_object_key(kind, filename)`，唯一性与命名规则的唯一出处。

`kind` 取值集中定义，V0.1.2 建立 `original`（原始视频）与 `clip`（切片），后续版本按需扩展常量，不改键结构。

### 3.2 异常体系

- `StorageError`：存储模块所有可预期失败的基类。
- `StorageClientError`：参数非法、网络/连接失败、凭据缺失等调用侧问题。
- `StorageServerError`：对象存储返回的非 2xx 服务端错误，携带 `code`、`request_id`、`status_code`。

`tos_backend` 在两个入口（初始化与各操作）统一映射 SDK 的 `TosClientError` / `TosServerError`。映射直接在 `except` 分支中构造领域异常而非事后重新读取属性，避免属性缺失导致二次失败。日志只记录 `code`/`request_id`/`message` 与对象键，严禁记录 AK/SK 与预签名 URL。

## 4. 配置与健康检查

### 4.1 配置扩展

`config.py` 在既有 `TOS_*` 占位基础上补齐真实所需项，并新增：

- `storage_backend`：`auto`（默认，有凭据用 TOS，无凭据回落 Mock 并在启动日志给出提示）、`tos`（强制真实，缺凭据时明确报错，测试环境使用）、`mock`（强制内存实现）。
- `tos_object_prefix`、`tos_presigned_ttl_seconds`。
- `storage_configured` 与 `storage_missing_fields`：判定存储是否可用并指出缺失项，供健康检查与自检命令复用，避免判定逻辑散落。

AK/SK 保持无默认值、只读环境变量，符合 V0.1.1 既有约定。

### 4.2 健康检查

`/health` 增加 `storage` 字段，三态：

- `configured`：凭据齐全，存储可用。
- `not_configured`：缺少必填项，服务仍可运行（V0.1.2 尚不依赖存储）。
- `unavailable`：已配置但初始化失败（如 SDK 缺失），此时整体 `status` 为 `degraded`。

`not_configured` **不**使整体状态降级：测试环境尚未配置凭据时服务仍应健康，且 `v0.1-plan.md` 明确「本地无 TOS 凭据不影响除 V0.1.2 之外版本的本地开发」。健康检查只验证配置完备性，不发起网络往返，避免探针被外部网络拖慢或误判。

## 5. 连通自检命令

`python -m app.storage.verify`（可加 `--keep` 保留对象以便人工在控制台检查，默认删除）执行：

1. 校验配置，缺失必填项时给出明确退出信息；
2. 生成随机内容的小文件（带时间戳命名，避免污染）；
3. 上传，打印对象键；
4. 生成预签名 URL，用标准库 HTTP 拉取该 URL 校验可访问，并比对 SHA256；
5. 用下载接口取回本地文件并比对 SHA256；
6. 删除对象，确认清理成功；
7. 逐项打印结果与总体结论，任一步失败即给出失败环节与原因（服务端错误含 `request_id`），退出码非 0。

放在 `app/storage/` 内而非 `tests/`，因为它需要真实凭据与网络，属运维自检而非单元测试；`docs/runbooks/deployment.md` 记录执行方式。

## 6. 错误处理与安全

- 配置缺失或非法时由 `get_storage()` 抛出明确异常，错误信息只列出缺失的字段名，不含字段值。
- 存储操作失败时不吞异常：映射为领域异常向上抛出，由调用方决定状态流转（V0.1.3 的任务失败记录）。
- 日志与异常文本中出现 AK/SK 视为缺陷，本地以单测断言日志内容不含凭据值。
- `.env`、SQLite 数据文件沿用既有 `.gitignore` 排除规则，新增内容不引入任何凭据落地。

## 7. 测试

**本地（Mock）**：

- 对象键：`kind` 分层结构、扩展名保留、同名文件多次生成不重复、时钟固定时唯一性仍成立。
- 上传/下载/读取/删除：往返内容一致；删除后可确认不存在。
- 预签名 URL：包含对象键与有效期参数。
- 异常映射：Mock 注入「客户端错误」与「服务端错误」两类故障，断言抛出正确的领域异常类型与字段。
- 凭据与日志脱敏：断言日志文本不含 AK/SK 值。
- 配置：`storage_backend` 三种取值的行为、`storage_configured` 判定、缺失字段列举。
- 健康检查：`storage` 三态与整体状态的对应关系（`not_configured` 不降级、`unavailable` 降级）。
- 既有 V0.1.1 测试全部回归通过。

**前端**：状态页渲染存储状态；`/health` 返回值缺少 `storage` 字段时不报错。

**测试环境**：`python -m app.storage.verify` 使用真实凭据跑通上传 → 预签名可访问 → 下载 → 删除；`docker compose up` 后健康检查通过且 `storage` 字段符合配置实际。

## 8. 验收要点（对应 v0.1-plan.md 第 4 节 V0.1.2）

- 本地：通过 Mock 验证存储模块的业务逻辑、异常处理与 object_key 唯一性（单测覆盖）。
- 测试环境：使用真实 TOS 凭据完成一次小文件的上传 → 生成预签名 URL（可访问）→ 下载 → 删除的连通验证。
- AK/SK 不出现在代码、日志与仓库中；服务端异常的 `request_id` 记录进日志。

## 9. 不在本版范围

- 上传接口、任务记录与进度状态（V0.1.3）。
- 分片上传、断点续传、大文件传输优化（V0.1.3 按需确定）。
- 对象列举、生命周期规则、跨域配置、桶管理等运维能力。
- 前端存储自检页、对象浏览页。
- 媒体探测与切分（V0.1.4、V0.1.5）。

## 10. 已知限制

- 本机未安装 Docker，compose 相关变更只做结构与语法自洽检查，拉起验证在测试环境执行。
- 本机无真实 TOS 凭据，`verify` 命令与真实连通性结论只能在测试环境得出；本地结论仅覆盖 Mock 路径。
