# V0.1.3.1 设计文档：删除已上传视频

> 本文是 V0.1.3.1（删除已上传视频）的设计文档，属 `specs/` 下的开发任务期间产出。
> 依据：`docs/specs/v0.1.3-design.md`、`docs/README.md` 文档规范。
> 定位：记录删除语义、清理顺序与并发守卫这几个不易从代码看出的决策；字段清单与函数签名不在此复述。

## 1. 目标

用户上传完成后可主动删除该视频，后台同步清除对象存储中的原始视频、本地分片与合并临时文件、任务与上传会话记录。

## 2. 选型与决策

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 接口主体 | 挂在任务上：`DELETE /api/tasks/{id}` | 前端只持有 `task_id`；当前上传会话与任务 1:1，挂在会话上会多出一套 id 概念而无额外能力 |
| 清理顺序 | 对象存储 → 本地产物 → 数据库记录 | 数据库行是唯一能再次定位对象与分片的线索。先删对象，失败即中止并保留记录，用户可原样重试；反过来先删记录会留下永远无法回收的孤儿对象 |
| 云端缺失对象 | 视为删除成功 | 沿用 `delete_object` 的幂等契约，不因对象已被移走而拒绝删除记录 |
| 本地清理失败 | 记 warning 后继续删除记录 | 分片目录残留只占磁盘、不产生语义问题；为此拒绝删除会让用户卡在无法删除的状态 |
| 并发守卫 | `uploading` / `processing` 状态返回 409 | 上传中原始视频尚未落存储，处理中执行器可能正在读写该对象，删除会制造半途而废的清理 |
| 重复删除 | 返回 404 | 删除是破坏性操作，静默成功会让用户误判「刚才那一下生效了」 |
| 记录范围 | 任务行与上传会话行一起删除 | 上传会话对用户没有独立意义，留下只会成为孤儿记录 |
| 未入库任务 | 允许删除 | 上传失败或中断的任务没有对象键，但本地留有分片；这正是需要清理的场景 |
| 前端交互 | 任务终态区提供「删除视频」，`window.confirm` 二次确认 | 不可撤销操作需要一次显式确认；确认文案写明清除范围，避免误以为只删本地记录 |

## 3. 模块边界

```
backend/app/
├─ deletion.py            # 新增：删除编排（存储 → 本地产物 → 记录）
├─ routers/tasks.py       # 新增 DELETE /api/tasks/{id}
└─ tasks/runner.py        # 新增 remove_task_records：删除任务行与其上传会话行
```

依赖方向沿用既有约定：`routers` → `deletion` / `tasks` / `storage`；`deletion` 复用 `chunks.cleanup()` 与存储契约，自身不接触供应商 SDK。

## 4. 接口语义

`DELETE /api/tasks/{id}`

- `204`：对象、本地产物与记录均已清除。
- `404`：任务不存在（含重复删除）。
- `409`：任务处于 `uploading` 或 `processing`。
- `502`：对象存储删除失败，记录保留，响应体含 `describe_error` 整理后的原因（服务端错误带 `request_id`）。

## 5. 前端

- 任务终态区（成功或失败，只要任务存在）展示「删除视频」按钮，与「重新执行任务」「换一个文件」同排，用警示色描边区分不可逆操作。
- 删除中按钮禁用并显示「删除中…」，避免重复提交。
- 删除成功后回到初始态；失败则在任务区展示后端原因，任务状态与对象键保持可见，便于重试。

## 6. 测试

**后端**（`tests/test_uploads.py`）：删除成功后对象、任务行、会话行、分片目录与合并临时文件全部消失；重复删除 404；`uploading` 与 `processing` 返回 409 且记录与分片保留；未知任务 404；存储删除失败返回 502 且记录保留、恢复后可再次删除；入库失败但留有分片的任务可删除并清掉残留。

**前端**（`UploadPanel.test.tsx`）：确认后调用删除接口并回到初始态；取消确认时不发起请求；删除失败展示后端原因且任务状态仍可见。

## 7. 不在本版范围

- 批量删除、回收站与恢复、孤儿对象定时清理。
- 多用户与鉴权（V0.1.3 起即不在范围内）。
- 删除正在处理中的任务（需要执行器配合取消，属后续版本）。
